# EAD-TASK-001 能力评估与差距分析报告

## 评估结论

Shanforge 当前可以支撑第一家客户的“咨询交付包 + AI 工作流试运行 + 交付闭环搭建”试点，但还不能直接作为开箱即用的企业 SaaS 工作台销售。

建议第一阶段定位为：

**企业 AI 交付闭环工作台实施包**

核心价值不是替客户写代码，而是把需求、估算、缺陷、验收、周报和复盘从口头沟通变成可审计、可追踪、有人审门禁的交付闭环。

## 客户问题判断

这不是单纯的“开发慢”问题，而是企业软件交付闭环缺失问题。

当前关键症状：

- 负责人缺少可向上汇报的交付事实，无法判断效率、风险和资源缺口。
- 业务和运营提交的是业务意图、截图、现象，开发收到后仍缺字段、规则、接口、页面、验收和测试样例。
- 估算不可解释，例如 20 人日记录缺少拆分依据，负责人无法判断是否合理。
- 缺陷记录缺少复现、根因、处理结果、测试证据和生产验证，关闭证据不足。
- 业务、运营、开发、测试、运维、负责人之间缺少共同 gate。

## 当前能力矩阵

| 能力类别 | 结论 | 说明 |
|---|---|---|
| 需求资料结构化 | 可直接复用 | 现有文档、表格、需求工程和模板能力可把 Word / Excel / 缺陷记录转成开发就绪输入 |
| Work item / ledger / evidence | 可直接复用 | 可沉淀需求、估算、执行、验证、review 和复盘证据 |
| Review / verification gate | 可直接复用 | 适合“AI 出草稿，人做确认，证据进闭环”的企业现场模式 |
| 估算拆解 | 需轻量包装 | 现有 plan/task 能表达拆分依据，但还需要企业估算模板和字段模型 |
| 缺陷闭环 | 需轻量包装 | 现有 evidence / verification 能承载闭环，但还需要缺陷字段、根因分类和关闭模板 |
| 周报看板 | 需新增能力 | 目前可生成报告，但缺面向负责人稳定看板和数据投影模型 |
| 企业工作台 UI | 需新增能力 | 当前 Shanforge 更偏工程化流程，不是业务/负责人可直接使用的产品界面 |
| 客户系统集成 | 暂不支持开箱即用 | 腾讯文档、金山文档、企业微信、工单、代码仓库等需后续连接器 |
| 自动替人决策 | 不应支持 | AI 只能生成结构化草稿、缺口、风险和建议，最终由人审 gate 决策 |

## Shanforge 能解决什么

1. 把散乱资料转成开发就绪输入。

   Shanforge 可以把需求文档、排期表、缺陷表和运维记录整理成背景、目标、范围、规则、字段、页面、接口、数据源、验收标准、测试用例、风险和待澄清问题。

2. 把估算从黑盒变成可解释。

   每个估算可以绑定需求拆分、技术影响、数据处理、前后端工作量、测试联调、上线验证、风险缓冲和未决问题。

3. 把缺陷关闭变成有证据的闭环。

   缺陷关闭前必须留下环境、影响范围、复现证据、根因分类、修复说明、测试证据、生产验证和回归沉淀。

4. 把负责人汇报变成周度事实看板。

   基于 work item、ledger 和 evidence，可生成本周需求状态、缺陷关闭状态、阻塞项、风险、需决策事项和下周计划。

## Shanforge 不能直接解决什么

- 不能直接提供面向企业业务、运营、开发、运维和负责人的 SaaS 工作台 UI。
- 不能直接读取客户内部腾讯文档、金山文档、企业微信、工单系统或代码仓库，除非客户授权并完成连接器。
- 不能替代客户负责人、业务、开发、测试、运维做最终决策。
- 不能仅凭现有缺失字段判断开发效率正常或异常，只能先补齐证据链。
- 不能在没有真实试点样本的情况下证明长期 ROI，只能先用 30 天试点验证。

## 多岗位协同评估

| 角色 | 责任 | Shanforge 支撑方式 |
|---|---|---|
| 业务/运营 | 提供业务目标、口径、范围、验收标准 | AI 生成缺失问题和开发就绪度，由业务/运营确认 |
| 产品/项目负责人 | 决策优先级、资源、范围和风险 | 周报看板、估算依据、阻塞清单和决策事项 |
| 开发 | 确认技术拆分、估算、接口/数据影响 | 估算拆解、技术风险记录、实现证据 |
| 测试/运维 | 确认验收方法、上线验证、生产关闭证据 | 验收清单、缺陷关闭标准、生产验证 evidence |
| AI Agent | 结构化、补字段、找缺口、生成草稿 | 输出受契约约束，必须进入人审 gate |
| Shanforge | 管理 work item、ledger、evidence、review gate | 保留可追踪交付记录和复盘沉淀 |

## 闭环设计评估

每个需求或缺陷至少要走完以下闭环：

1. 输入：原始资料进入 Shanforge。
2. 结构化：AI 生成标准字段、缺失问题和风险。
3. 人审：对应岗位确认事实、范围和决策。
4. 执行：开发、测试、运维按确认后的任务执行。
5. 验证：测试环境和生产环境留下证据。
6. 复盘：AI 生成周报、根因、知识库和下一步改进。
7. 沉淀：Shanforge ledger、evidence、memory 形成可追踪记录。

## 30 天试点可行性

建议试点范围：

- 选取 2 个真实需求：`项目统计基数调整需求`、`实名制管理数据统计优化`。
- 选取一批正式环境 / P0 / P1 缺陷记录。
- 第一阶段采用人工导入导出，不接入客户生产系统。
- 先交付咨询包和半自动 Agent 流程，暂不承诺完整 SaaS。

试点节奏：

| 周期 | 重点 | 产物 |
|---|---|---|
| 第 0 周 | 资料收集和基线诊断 | 字段完整率、缺陷闭环完整率、估算可解释率基线 |
| 第 1 周 | 需求准入和开发就绪包 | 两个需求的缺失问题清单和开发就绪包 |
| 第 2 周 | 估算拆解和验收设计 | 估算拆分、风险前提、验收用例、上线验证清单 |
| 第 3 周 | 缺陷闭环试运行 | 缺陷归因、关闭标准、验证证据补齐 |
| 第 4 周 | 周报看板和复盘 | 负责人周报、试点指标、第二阶段建议 |

## 验收指标

- 原始 Word / Excel 到开发就绪包初稿不超过 1 个工作日。
- AI 生成字段经业务、开发、运维确认后的保留率不低于 80%。
- 核心需求字段完整率提升到 90% 以上。
- 进入排期的需求必须有拆分依据和风险前提。
- 关闭缺陷必须包含处理结果、验证证据和根因分类。
- 每周生成负责人可用的进度、风险和决策清单。

## 最终判断

可以进入下一步产品化设计，但必须保持边界：

- 先做试点实施包，不先做完整 SaaS。
- AI 负责结构化和建议，人负责确认和决策。
- Shanforge 负责证据链、review gate、verification gate 和交付知识沉淀。
- 第二阶段是否做轻量 Web 工作台，要等 30 天试点验证指标后再决定。
