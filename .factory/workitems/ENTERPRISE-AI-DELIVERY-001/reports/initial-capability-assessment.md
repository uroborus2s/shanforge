# 企业 AI 软件工程化与交付闭环初始能力评估

## 结论

Shanforge 当前能力可以支撑第一家客户的“咨询 + AI 工作流试运行 + 交付闭环搭建”试点，但还不能直接包装成开箱即用的企业 SaaS 产品。

建议第一阶段的产品形态不是单纯卖项目管理咨询，也不是单纯卖 AI 编程工具，而是：

**企业 AI 交付闭环工作台实施包**

交付价值是让负责人从“听各方解释、凭感觉判断”变成“看需求是否开发就绪、看估算是否可解释、看缺陷是否闭环、看每周风险和决策清单”。

## 客户现场的真实痛点

### 负责人痛点

- 不懂软件细节，无法判断开发说“需求不清楚”是真问题还是借口。
- 缺少可向上汇报的数据依据，无法证明团队效率、风险和资源缺口。
- 任务评估是黑盒，20 人日是否合理没有拆分依据。
- 缺陷和生产问题很多，但看不出根因是需求、数据、代码、环境、协同还是历史债务。
- 新需求、历史问题、线上故障混在一起，负责人只能救火，不能治理。

### 业务和运营痛点

- 他们认为已经把问题提出来了，但开发仍然认为不能做。
- 需求记录和缺陷记录缺少统一模板，导致同一件事反复解释。
- 处理结果、验收状态、上线验证经常不透明。
- 业务口径变更没有形成稳定的版本记录，后续统计异常难以追责。

### 开发团队痛点

- 收到的是业务意图、截图和现象，不是开发就绪需求。
- 缺少字段、接口、页面、规则、异常、历史数据处理、验收标准和测试样例。
- 一旦评估或延期，容易被理解为效率低，而不是输入不足或风险未澄清。
- 缺陷记录缺少复现路径、环境、影响范围、期望结果和生产验证，修复后仍可能反复。

### 企业层面痛点

- 系统已经在线运行，后台、小程序和 App 牵涉真实业务，一旦统计口径或实名制数据异常，会影响管理决策。
- 3 人维护开发团队对系统知识和历史逻辑高度集中，人员变化风险高。
- 交付资料没有沉淀为知识库，新人、负责人和外部顾问很难快速接管。

## 已识别证据

| 资料 | 主要发现 | 对交付闭环的影响 |
|---|---|---|
| `工作簿1.xlsx` | 需求排期字段缺少优先级、估算依据、计划日期、完成日期、验收记录、需求说明链接 | 无法判断开发效率是否正常，也无法复盘延期原因 |
| `工作簿2.xlsx` | 问题记录中正式环境/P0 类问题占比高，截图、处理结果、生产验证、根因字段不足 | 缺陷无法形成关闭证据，线上问题容易反复 |
| `专业分包单位和企业劳务管理数据上线需求.docx` | 有业务方向，但缺少开发范围、角色权限、字段映射、页面变化、验收标准 | 不能直接进入开发，必须先转成开发就绪包 |
| `项目统计基数调整需求说明.docx` | 涉及智慧工地参数、项目状态、标签、境外项目、合同模式、历史映射和统计口径 | 20 人日可能合理，但现有记录缺少拆分依据，负责人无法判断 |
| `实名制管理统计优化.docx` | 涉及 A/B/C/D 项目分类、MainDataSource、Mongo 实时考勤、手动表和上线率 | 依赖统计口径和数据源澄清，未估算不应直接排期 |

## Shanforge 当前可直接解决的部分

### 1. 把散乱资料转成结构化交付输入

通过现有 docx、xlsx、requirements-engineering、document-templates 能力，可以把 Word、Excel 和表格记录转成：

- 需求背景和目标。
- 范围和非范围。
- 业务规则。
- 字段和数据口径。
- 页面、接口、数据源影响。
- 待澄清问题。
- 验收标准。
- 测试用例。
- 风险和依赖。

### 2. 把任务评估从“拍脑袋”变成“可解释”

通过 writing-plans、executing-plans 和 work item plan 模型，可以要求每个估算都关联：

- 需求拆分。
- 技术影响面。
- 数据迁移或历史修复。
- 前端、后端、测试、联调、上线验证工作量。
- 风险缓冲。
- 估算前提和未决问题。

这样可以回答“20 人日是否合理”：不是直接判断合理或不合理，而是让开发必须把估算拆成可审计结构，负责人再基于证据决策。

### 3. 把缺陷处理变成闭环

通过 ledger、evidence、verification-before-completion 和 review gate，可以要求每条缺陷关闭前必须具备：

- 环境。
- 影响范围。
- 复现路径或证据。
- 根因分类。
- 修复说明。
- 测试证据。
- 生产验证。
- 是否沉淀规则或回归用例。

### 4. 把负责人汇报变成周度看板

Shanforge 的 work item 和 ledger 可以沉淀每周事实，再由 AI 生成：

- 本周新增需求、已进入开发需求、被阻塞需求。
- 本周线上问题、已关闭问题、未验证问题。
- 需要负责人决策的优先级、资源、范围和风险。
- 开发团队产能和主要阻塞。
- 下周计划和风险提示。

## 当前不能直接解决的部分

### 1. 还没有企业工作台产品界面

Shanforge 目前更像工程化流程和 agent 运行体系，不是给业务、运营、负责人直接使用的企业产品界面。第一家客户可以用半自动导入导出和顾问交付方式试点，但要规模化销售，需要工作台界面。

### 2. 还没有面向企业资料的固定数据模型

需要新增统一模型：

- 需求准入模型。
- 开发就绪包模型。
- 估算拆解模型。
- 缺陷闭环模型。
- 周报看板模型。
- 决策事项模型。

### 3. 还没有专门的企业交付 Agent

需要把现有通用 skills 包装成企业现场能理解的 Agent：

- 需求准入 Agent。
- 开发就绪包 Agent。
- 估算拆解 Agent。
- 验收用例 Agent。
- 缺陷归因 Agent。
- 周报看板 Agent。

### 4. 还没有客户系统集成

腾讯文档、金山文档、Excel、企业微信、代码仓库、工单系统都可能是客户资料来源。第一阶段可以用导入导出，后续再做连接器。

## 解决方案设计

### 产品形态

名称建议：

**Shanforge 企业 AI 交付闭环工作台**

第一阶段包装为服务产品：

- 诊断咨询：梳理现有需求、缺陷、排期和交付证据。
- AI 工作流配置：为客户配置需求、估算、缺陷、周报 Agent。
- 试运行陪跑：选取 2 个需求和一批缺陷跑通闭环。
- 管理看板：每周向负责人输出风险、决策和改进报告。

### Agent 工作流

| Agent | 输入 | 输出 | 人审门禁 |
|---|---|---|---|
| 需求准入 Agent | Word、表格、聊天记录、截图说明 | 缺失字段清单、澄清问题、是否可进入开发判断 | 业务/运营确认口径和范围 |
| 开发就绪包 Agent | 需求说明、澄清回答、历史资料 | 范围、非范围、规则、字段、页面、接口、验收标准 | 产品/负责人确认优先级和范围 |
| 估算拆解 Agent | 开发就绪包、系统背景、历史任务 | 前后端/数据/测试/联调/上线拆分和估算依据 | 开发确认技术可行性和工作量 |
| 验收用例 Agent | 开发就绪包、业务规则 | 测试用例、异常场景、回归点、上线验证清单 | 测试/运维确认验收方法 |
| 缺陷归因 Agent | 缺陷记录、环境、日志、截图、处理过程 | 根因候选、缺失证据、修复建议、关闭检查项 | 开发/运维确认根因和修复证据 |
| 周报看板 Agent | work item、ledger、缺陷和需求状态 | 本周进度、阻塞、风险、需决策事项、下周计划 | 负责人确认决策事项和汇报口径 |

### 多岗位协同闭环

| 环节 | 业务/运营 | 产品/项目负责人 | 开发 | 测试/运维 | AI Agent | Shanforge |
|---|---|---|---|---|---|---|
| 需求提出 | 提交目标、场景、截图、口径 | 初筛优先级 | 提供历史限制 | 提供环境和数据约束 | 生成缺失问题 | 建立 work item |
| 需求准入 | 回答澄清问题 | 确认是否进入开发 | 标记技术未知项 | 标记验收风险 | 输出开发就绪度 | 记录 gate |
| 估算排期 | 确认业务期限 | 决策优先级和资源 | 拆分工作量和风险 | 补测试/上线成本 | 生成估算结构 | 记录估算依据 |
| 开发执行 | 响应口径变化 | 处理阻塞和范围变化 | 实现并提交证据 | 准备测试环境 | 检查遗漏和一致性 | 记录 evidence |
| 验收上线 | 确认业务结果 | 确认上线窗口 | 修复问题 | 验证生产结果 | 生成验收清单 | 记录 verification |
| 复盘周报 | 反馈满意度 | 决策改进项 | 沉淀技术原因 | 沉淀运维原因 | 生成周报和知识库 | 更新 ledger/memory |

### 闭环定义

每个需求或缺陷必须走完以下闭环，才允许关闭：

1. 输入：原始资料进入 Shanforge。
2. 结构化：AI 生成标准字段、缺失问题和风险。
3. 人审：相关岗位确认事实和决策。
4. 执行：开发、测试、运维按确认后的任务执行。
5. 验证：测试环境和生产环境留下证据。
6. 复盘：AI 生成周报、根因、知识库和下一步改进。
7. 沉淀：Shanforge ledger/evidence/memory 形成可追踪记录。

## 第一家客户 30 天试点

### 第 0 周：诊断和资料接入

- 收集近一个季度需求、缺陷、排期和运维记录。
- 选定两个需求：`项目统计基数调整需求`、`实名制管理数据统计优化`。
- 选定一批正式环境/P0/P1 缺陷记录。
- 建立试点指标基线：字段完整率、缺陷关闭完整率、估算可解释率。

### 第 1 周：需求准入和开发就绪包

- 用 AI 把两个需求转成开发就绪包。
- 输出缺失问题清单。
- 让业务、运营、开发分别确认。
- 产出第一版需求准入模板。

### 第 2 周：估算拆解和验收设计

- 让 AI 生成任务拆分、估算依据和风险。
- 开发团队确认或修正估算。
- 生成验收用例和上线验证清单。
- 负责人获得“为什么是这个工作量”的汇报依据。

### 第 3 周：缺陷闭环试运行

- 对历史缺陷记录做字段补齐和归因分类。
- 选取仍未验证或缺少处理结果的问题补齐证据。
- 建立缺陷关闭标准。

### 第 4 周：周报看板和复盘

- 自动生成负责人周报。
- 汇总需求准备度、估算可解释性、缺陷关闭完整性、阻塞事项。
- 输出是否进入第二阶段的决策建议。

## 试点验收指标

- 需求开发就绪包生成时间：从原始 Word/Excel 到初稿不超过 1 个工作日。
- AI 生成字段采纳率：业务、开发、运维确认后保留字段不少于 80%。
- 需求字段完整率：核心字段完整率从当前不可审计提升到 90% 以上。
- 估算可解释率：进入排期的需求必须有拆分依据和风险前提。
- 缺陷关闭完整率：关闭缺陷必须包含处理结果、验证证据和根因分类。
- 周报自动化率：每周自动生成负责人可用的进度、风险和决策清单。

## 后续 Shanforge 产品化 backlog

- 新增 `enterprise-ai-delivery-loop` 正式需求文档和实施方案。
- 新增企业资料样例 fixtures，用于 Word/Excel/缺陷记录解析评估。
- 新增需求准入、缺陷闭环、周报看板相关 skill 或 reference。
- 新增 Agent 输出契约测试，检查字段完整率、占位语、缺失证据和 gate 状态。
- 评估轻量 Web 工作台：角色视图、需求列表、缺陷列表、周报看板、证据链。
- 设计 Qoder/agent 工具结合方式：代码实现可由 Qoder 辅助，Shanforge 负责需求、任务、review、验证和交付闭环。

## 与 Qoder/agent 工具的结合

Qoder 等 agent 编程工具适合提升代码实现效率，但客户问题不是“缺一个写代码工具”，而是“需求、估算、执行、验收、复盘没有闭环”。

建议分工：

- Shanforge：负责需求工程、任务拆分、证据链、review gate、验证 gate、周报和知识沉淀。
- Qoder/agent 编程工具：负责在开发确认后的任务包内辅助实现、改代码、生成测试、解释代码影响。
- 企业团队：负责业务确认、技术确认、上线确认和管理决策。

这样 AI 增效不是停留在“写代码更快”，而是覆盖：

- 需求更快进入开发就绪状态。
- 估算更透明。
- 开发过程更可追踪。
- 缺陷关闭更规范。
- 负责人汇报更有依据。

## 风险与应对

| 风险 | 应对 |
|---|---|
| 客户资料不允许系统接入 | 第一阶段采用人工导入导出和脱敏样本 |
| 开发团队抵触被考核 | 明确 AI 是补齐输入和证据，不直接评价个人 |
| 业务不愿补充字段 | 用准入门禁说明缺字段不能排期，负责人参与决策 |
| 试点样本太小，价值不明显 | 至少覆盖 2 个需求和一批真实缺陷记录 |
| 只做咨询不可复制 | 所有模板、Agent 输出契约和指标必须沉淀到 Shanforge |
