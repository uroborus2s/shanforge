# HUMAN-RESPONSE-CONTRACT-002：按工作类型输出可理解的开发状态

## 状态

`ready_for_commit`

## 来源

- 用户要求优化使用 Shanforge skills 开发软件项目时的会话响应。
- 用户明确关注：开发到哪一步、哪些功能完成或未完成、测试总数与结果、失败原因、Bug 根因，以及修复是否创建新任务卡。
- 本工作项是已关闭 `HUMAN-RESPONSE-CONTRACT-001` 的后续变更；保留三段式外壳，补齐按工作类型变化的正文合同。

## 目标

让 AI 在项目化开发会话中先用业务语言说明当前结论，再按当前工作类型展示足够的进度、测试或缺陷事实；内部 ID、Gate、路径和命令只作为末尾证据，不代替解释。

## 需求

### HRC-REQ-001：共享状态头

所有项目化进度更新都说明当前阶段、当前任务、已完成结果、剩余范围、阻塞和唯一下一动作。没有完整 WBS 或测试基线时明确写“无法计算”，不得猜测百分比或分母。

### HRC-REQ-002：开发响应以 WBS 为范围

- 开发任务以已批准 WBS、TaskCard 和 ledger 为事实源。
- 区分已完成、进行中、未开始和阻塞项；系统治理、评审、提交等任务不得冒充产品功能进度。
- 每个已完成项说明可观察结果和验证状态，不只显示状态码。

### HRC-REQ-003：测试响应以测试基线和报告为范围

- 使用测试计划、测试案例目录和本轮测试报告说明总数、通过、失败、错误、阻塞、跳过、未运行和取消数量。
- 每个失败或错误项说明测试 ID、关联功能、可观察现象和当前归因；根因未知时明确写“待调查”，不得猜测。
- 说明本轮测试覆盖什么、未覆盖什么，局部通过不得表述为项目通过。

### HRC-REQ-004：Bug 响应解释问题而不是只报状态

Bug 调查或修复响应必须说明现象、影响、复现、直接原因、根源原因、事实 owner、风险、修复状态和回归验证。尚未定位根因时只报告已知事实和下一项诊断动作。

### HRC-REQ-005：修复任务卡决策

- 当前任务验收前发现、同一根因、同一允许范围且可在原验收内修复的缺陷，作为原任务整改，不新建 TaskCard。
- 已交付或已验收功能的回归、跨任务/模块/owner、超出允许范围、高风险或生产缺陷、需要独立排期/依赖/验收的缺陷，创建 Bug TaskCard。
- 多个失败用例同一根因只创建一张 Bug TaskCard；测试预期、夹具、脚本、配置或环境错误回对应 owner，不创建产品 Bug TaskCard。
- 新 Bug TaskCard 关联失败 `TEST-*`、受影响 `REQ-*`/WBS 项、来源任务和根因证据。

### HRC-REQ-006：观察格式行为验证

测试必须验证合同的语义字段和决策边界，不只检查“三段式”“已完成”等标题存在。

## 验收标准

- `using-shanforge` 保留三段式外壳，并增加开发、测试、Bug/修复、评审/交付的正文选择规则。
- 工作 Skill 回写合同保留专业状态，同时携带人类摘要、进度变化、验证摘要和适用的缺陷摘要。
- `systematic-debugging`、`tdd-workflow`、`verification-before-completion` 的状态包能提供总控所需事实。
- 修复任务卡决策表可判定原任务整改、新 Bug TaskCard、测试/环境 owner 三种结果。
- 定向测试和相关合同测试通过；不新增运行时、数据库或依赖。
- 用户指南说明如何阅读开发、测试和 Bug/修复响应。

## 非目标

- 不新增 PM 页面、状态数据库、中心运行时或新的通用响应 Skill。
- 不要求每条 commentary 重复完整报告；完整状态只在任务开始、阶段变化、测试结束、Bug 归因、阻塞和最终收口时输出。
- 不修改 `SOFTWARE-LIFECYCLE-GOVERNANCE-001` 或其他工作项事实。

## 影响分析

- baseline 影响：修改流程总控与工作 Skill 交接合同，不改变产品架构、数据 schema、外部 API 或发布方式。
- 风险：`medium`；若各专业 Skill 字段与总控不一致，会继续产生可读性漂移。
- 分析模式：`embedded`；定位为本 brief 的“需求、验收标准与影响分析”。
