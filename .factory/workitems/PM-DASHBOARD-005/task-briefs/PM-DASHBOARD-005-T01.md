# PM-DASHBOARD-005-T01：生成完整阶段化项目看板

- 状态：`approved_pending_human_ui_acceptance`
- 类型：`UI 实现`
- 任务层级：`cross_cutting`
- 优先级：`P0`
- 需求模块：`项目管理 / 项目可视化`
- 关联需求：`REQ-PM-SNAPSHOT-001`、`REQ-PM-SNAPSHOT-002`、`REQ-PM-SNAPSHOT-003`、`REQ-PM-SNAPSHOT-004`、`REQ-PM-SNAPSHOT-005`、`REQ-PM-SNAPSHOT-006`、`REQ-PM-SNAPSHOT-007`、`REQ-PM-SNAPSHOT-008`

## 目标

把被退回的日志式页面重做为 6 个负责人视图：产品主线与看板维护分开，当前任务进入
六列敏捷看板并显示需求模块和任务类型，技术文档以站内可读 HTML 打开，审计细节默认下沉。

## 验证

快照合同测试通过；真实 Shanforge 页面在桌面和移动视口完成 30 秒接手判断、文档入口、内容层级、溢出、键盘与控制台验收。

## 当前人工反馈

- 结构栏目存在，但内容仍是内部工作项、技术术语、路径和事件日志，无法支持半途接手的项目负责人判断项目目标、主线进度、关键路径、交付状态和待决事项。
- 当前候选不得提交或关闭；先重做管理信息投影和内容层级，再进行 UI 验收。
- 第二轮 UI 验收确认：首页没有正式要求的六列敏捷看板；任务、需求和计划不可点击；文档链接直接打开 Markdown 源文件；项目介绍、最终交付、整体计划和可核验进度缺失。上一轮独立代码复审不构成真实负责人可用性验收。
- 第三轮 UI 验收确认：六列看板仍按状态平铺，未实现“需求分组后再按任务层级和类型分类”；当前工作卡没有详情链接；6 个负责人视图仍在同一长页面，返回会丢失位置；路线图没有从项目、阶段逐层下钻到任务和每日进展。
- 第四轮 UI 验收确认：移动端路线图入口不可发现且路线图只有部分卡可点击；看板把缺失元数据直接显示为“未拆分独立需求 / 未登记”，没有按项目任务、需求任务等性质形成可理解分组；整张任务卡也没有明确点击反馈。
- 第五轮 UI 验收确认：路线图顶部阶段仍不可点击，无法从阶段逐层进入任务和每日进展；
  看板把任务性质、需求/工作项、专业分类和任务卡全部渲染成嵌套边框，分类没有使用标签，
  分组没有使用可展开收回面板。
- 第六轮 UI 验收确认：5 个阶段虽可点击，但都只进入同一总计划页的不同锚点，03 没有
  自己的子路线；看板虽改为折叠和标签，仍按状态优先切分全部 174 个任务，分组分类无法
  支持负责人快速判断当前工作。
- 第七轮 UI 验收确认：路线结构不能只依赖 H3–H6，必须改为显式 `parent_id` 并支持
  任意层级；当前看板在仅 7 张任务卡时仍生成 5 个默认展开泳道和 30 个状态单元，
  还与上方当前工作重复并混入全部活动技术工作项，信息密度和范围继续失控。

## 已确认整改方案

- 保留 10 类底层项目内容，收敛为项目总览、路线图、当前工作、阻塞与决策、交付就绪、文档与审计 6 个负责人视图。
- 产品主线由当前会话卡定位、由主线工作项最新 ledger 校正；看板维护任务只作为并行项目管理改进展示。
- 技术文档按需求、设计、开发、测试、发布与运维分类，并提供快速打开入口。
- 任务、需求、完整计划和正式文档均有独立可读页面与返回路径。
- 首屏展示当前 `skill-first` 产品定义、解决的问题、交付边界和主线 `2 / 5` 进度。
- 6 个负责人视图改为 6 个独立静态页面，共享页首 Tab；详情页返回所属模块。
- 看板状态列内按需求分组，需求组内按任务层级和类型分类，任务与需求均可点击。
- 路线图从项目主线进入计划阶段和任务，任务详情按 ledger 日期展示真实每日进展。

## 第四轮已批准修复方案

- 状态列内先按任务性质分组；需求任务再按需求分组，专业类型改为标签和组内分类。
- 多需求任务使用第一个正式关系作为唯一主分组，其他需求继续显示可点击名称和 ID。
- 移动端保留直接可见的页首 Tab，当前工作增加“查看分层路线图”入口。
- 当前工作和路线图中的每张可见卡都有明确文字操作，不依赖 hover 或仅标题点击。
- 快照投影区分任务事件和工作项 closeout 事件；终态只被显式 reopen /
  changes requested 覆盖。
- 原始任务简报缺失字段只在详情审计中说明，不再冒充业务分组。

## 第五轮已确认根因

- 路线图渲染器丢弃已有阶段 locator，顶部 5 个阶段生成静态卡；第四轮浏览器合同又排除
  `.stage-card`，因此工作项链接通过但阶段仍是 `0/5` 可点击。
- 渲染器把任务性质、需求/工作项、专业分类和任务全部当成独立 surface，且业务分组
  不是原生折叠结构；自动化只检查层级 class，没有检查视觉职责和折叠语义。
- 用户原话“确认以上两个根因”已关闭根因确认门。

## 第五轮已批准修复方案

- 复用现有阶段 ID，让顶部 `5/5` 阶段进入计划页稳定锚点；已拆任务继续进入任务详情和
  每日 ledger，未拆任务显示真实空态。
- 需求/工作项改为原生 `<details>/<summary>` 折叠面板；任务性质和专业分类改为标签。
- 视觉深度限制为“状态列 + 一个业务分组面板”，任务改为分隔线列表，不再框套框。
- 测试先固定链接目标、折叠语义和 surface 上限；实现后做 390×844、1440×900
  浏览器验收、独立评审和用户 UI 验收。
