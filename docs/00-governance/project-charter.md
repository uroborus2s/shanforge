## 1. 项目背景

- 当前业务背景：本仓库正在建设一套运行在 `Codex` 与 `Gemini CLI` 之上的软件工厂体系，用统一脚本、共享 skills、阶段化文档和控制面约束软件交付流程。
- 当前痛点：项目已经完成 `docs/` 基线建设，但仍需要防止旧路径和旧说明残留造成新的理解分叉。
- 启动原因：需要把与软件工厂项目本身相关的人类说明文档全部固定到 `docs/`，并删除 `workflows/` 下的相关副本，进一步降低接手成本。

## 2. 目标与成功标准

- 目标 1：保持 `docs/` 作为软件工厂项目唯一正式人类文档入口。
- 目标 2：删除 `workflows/` 中与软件工厂项目本身相关的人类说明文档副本。
- 目标 3：保持 CLI-first 的产品定位清晰，明确 `docs/`、专项 `workflows/` 和 `.factory/` 各自职责。

| 指标 | 目标值 | 度量方式 |
|---|---|---|
| 文档入口完整度 | 建立 1 套最小文档包，覆盖治理、调研、需求、设计、使用和追踪 | 检查 `docs/` 目录 |
| 可发现性 | 新协作者可在 10 分钟内定位项目定位、设计入口和用户指南 | 人工走查 |
| 一致性 | 默认配置和项目规则中的人类文档入口只指向 `docs/` | 检查 `config/software-factory.defaults.json` 与相关说明 |
| 清理完成度 | `workflows/` 下不再保留软件工厂项目本身的人类说明文档 | 文件清单检查 |
| 可演进性 | 每份正式文档都具备更新时间与变更记录 | 文档结构检查 |

## 3. 范围与非目标

### 范围内

- 维护 `docs/` 目录中的正式文档结构与阅读路径。
- 把原先留在 `workflows/` 的软件工厂项目相关人类说明文档并入 `docs/`。
- 更新项目默认配置、skill 引用和脚本生成规则，使 `docs/` 成为唯一正式人类文档入口。

### 范围外

- 当前不建设独立 API 平台或常驻编排服务。
- 当前不补齐整套发布、运维、管理员和合规文档。
- 当前不删除与其他专项 skill 直接绑定的非项目型 `workflows/` 文档。

## 6. 风险与假设

| ID | 类型 | 描述 | 影响 | 缓解措施 | 负责人 |
|---|---|---|---|---|---|
| `RISK-001` | 文档治理 | 代码、脚本和文档持续演进后，`docs/` 可能与真实实现脱节 | 中 | 把 `docs/` 作为正式入口，并要求行为变更同步更新 | 维护者 |
| `RISK-002` | 结构复杂度 | 仓库同时存在 `docs/`、专项 `workflows/`、`skills/` 和脚本，读者可能混淆层次 | 中 | 在 `docs/README.md` 明确职责边界和阅读路径 | 维护者 |
| `RISK-003` | 范围膨胀 | 一次性补齐全生命周期文档会导致大量空壳文档 | 中 | 采用最小可用文档包，按阶段继续补齐 | 维护者 |

假设：

- 当前产品边界仍以 CLI-first 为主，不以 API 平台为当前阻塞项。
- `docs/` 已经是软件工厂项目的人类正式事实来源。
- `workflows/` 仅保留与特定 skill 或专项流程直接绑定的辅助资料，不再承载软件工厂项目本身的人类说明。
