## 1. 背景与问题

- 历史背景：仓库曾经主要依赖 `scripts/`、`skills/`、`config/` 和 `workflows/` 长文档组织项目说明，后来才逐步建立正式 `docs/`。
- 触发原因：用户希望在项目中增加 `docs` 文件夹，组织和编辑山海工枢项目的需求规划、设计和用户使用文档。
- 需要解决的核心问题：给人类一个统一、清晰、可维护的正式阅读入口，同时不打断现有 CLI-first 工作方式。

## 2. 用户意图

- 想达到什么结果：在仓库中建立正式 `docs/` 目录，沉淀项目级需求、设计和使用文档。
- 为什么现在做：当前文档入口分散，新协作者理解成本较高，且正式文档与背景文档边界不清晰。
- 成功的直观判断：读者只看 `docs/` 就能理解项目定位、怎么工作、怎么继续维护。

## 3. 已知约束

- 时间约束：先落最小可用文档包，不创建大量空壳文件。
- 技术约束：当前产品仍是 CLI-first，文档必须和现有脚本、skills、配置保持一致。
- 资源约束：在当前仓库内直接整理，尽量复用已有长文内容与模板资产，避免重复写作。
- 不做的范围：本轮不补齐完整发布、运维、管理员和合规文档。

## 4. 方案探索

### 方案 A：维持 `workflows/` 作为唯一正式文档入口

- 核心思路：不新增 `docs/`，继续依赖现有合并版长文档。
- 优点：改动最小，不需要更新配置和引用。
- 缺点：需求、设计和使用文档混在一起，生命周期边界不清晰；不利于后续阶段化演进。
- 适用条件：项目很小、只有少量维护者，且不计划做进一步治理。

### 方案 B：建立最小可用 `docs/` 文档包并切换默认入口

- 核心思路：新增 `docs/`，只创建真正会被使用的治理、调研、需求、设计、使用和追踪文档；后续再清理软件工厂项目相关的 `workflows/` 副本。
- 优点：结构清晰、维护成本可控，能快速形成正式入口，同时不破坏现有脚本和历史资料。
- 缺点：需要同步更新配置和部分 skill 说明，避免文档入口分裂。
- 适用条件：当前仓库需要提升可读性和可交接性，但暂时不想一次性铺满全生命周期文档。

### 方案 C：一次性铺满完整生命周期文档目录

- 核心思路：按模板创建从治理到运维、交接、演进的完整目录和几十个文档。
- 优点：目录看起来最完整，后续阶段可直接填充。
- 缺点：空壳文档很多，当前维护成本高，容易造成“形式完整但内容空洞”。
- 适用条件：已经进入严格流程治理、多人并行、强合规或准备大规模交付的项目。

### 推荐方案

- 结论：采用方案 B。
- 推荐理由：它最符合当前仓库规模和当前目标，既能快速形成正式文档入口，也能为未来继续补齐发布、运维和交接文档留下自然扩展路径。
