# 产品需求文档（PRD）

**项目名称：** 山海工枢 / shanforge  
**文档状态：** 已确认基线  
**负责人：** 仓库维护者  
**主要读者：** 产品 | 架构 | 开发 | 测试 | 业务方  
**上游输入：** 头脑风暴记录 | 项目章程 | 当前 `docs/` 正式文档体系  
**下游输出：** 架构设计 | 测试计划 | 实施计划  
**关联 ID：** `REQ-001`, `REQ-002`, `REQ-003`, `REQ-004`, `REQ-005`, `REQ-006`, `REQ-007`, `NFR-001`, `NFR-002`, `NFR-003`  
**最后更新：** 2026-03-27  

## 1. 背景与目标

### 背景

本项目的目标不是做一个“自由发挥、直接写完整个项目”的单体模型，而是做一套可约束、可追踪、可协作、可持续演进的软件工厂体系。

当前仓库已经沉淀了共享 skills、`factory-*` 脚本入口、默认配置和项目骨架，也已经形成一套按生命周期组织的 `docs/` 正式文档体系。

当前这轮 PRD 的重点已经从“建立首批 `docs/` 基线”转为“把与软件工厂项目本身相关的人类说明文档全部收敛到 `docs/`，并消除 `workflows/` 与 `docs/` 的双入口混乱”。

### 业务目标

- 建立软件工厂项目自己的正式文档体系。
- 清晰表达 CLI-first 的产品范围、核心能力和边界。
- 为维护者、协作者和使用者提供一致的阅读入口。
- 让需求、设计与用户使用说明具备可追踪关系。

### 成功指标

| 指标 | 目标值 | 观测方式 |
|---|---|---|
| 文档体系覆盖度 | 建立覆盖治理、调研、需求、设计、使用和追踪的最小文档包 | 检查 `docs/` |
| 使用入口清晰度 | 使用者在 10 分钟内找到推荐命令和常见流程 | 人工走查用户指南 |
| 设计可追踪性 | 每条核心需求都能映射到设计文档、模块或接口 | 检查追踪矩阵 |
| 配置一致性 | 默认人类文档引用和项目规则文件都指向 `docs/` | 检查默认配置与规则刷新结果 |

## 2. 用户与场景

| 用户角色 | 场景 | 核心诉求 |
|---|---|---|
| 仓库维护者 | 维护脚本、skills、规则和文档 | 要有清晰的正式文档入口和变更边界 |
| 项目协调者 | 组织阶段推进和文档同步 | 需要看到需求、设计和追踪关系 |
| Codex/Gemini CLI 使用者 | 在业务项目里使用软件工厂工作流 | 需要快速知道怎么启动、接手、推进任务 |
| 新协作者 | 第一次接触该仓库 | 需要低成本理解项目定位、关键命令和架构边界 |

## 3. 功能需求

### `REQ-001` 建立并固化正式的人类文档入口

- 优先级：P0
- 描述：项目必须提供按生命周期组织的 `docs/` 目录，并将其固化为面向人类的唯一正式阅读入口。
- 用户故事：作为仓库维护者，我希望项目有结构化的正式文档入口，以便协作者无需先读代码也能理解项目。
- 前置条件：仓库已有脚本、skills、配置和历史长文档。
- 业务规则：`docs/` 作为正式事实来源；与软件工厂项目本身相关的人类说明文档不得继续留在 `workflows/` 中。
- 依赖项：无。
- 排除范围：不要求本轮补齐完整运维、发布和管理员文档。

验收标准：

- AC-1: 给定当前仓库，当查看根目录时，则能看到 `docs/` 及其最小文档包。
- AC-2: 给定新协作者，当阅读 `docs/README.md` 时，则能定位项目定位、主要文档和推荐阅读路径。
- AC-3: 给定默认配置、项目规则刷新或人类说明入口发生变化，当检查相关文件时，则能看到它们统一引用 `docs/`。

### `REQ-002` 形成需求规划与设计基线

- 优先级：P0
- 描述：项目必须把需求规划、需求分析、需求校验和核心设计文档整理为正式单文件。
- 用户故事：作为项目协调者，我希望需求与设计以结构化文档存在，以便阶段推进时有稳定事实来源。
- 前置条件：已明确项目定位为 CLI-first 软件工厂。
- 业务规则：需求和设计文档采用稳定 ID，并保持单文件持续演进。
- 依赖项：`REQ-001`
- 排除范围：不要求本轮补齐所有实现细节或所有阶段文档。

验收标准：

- AC-1: 给定需求阶段，当进入 `docs/02-requirements/` 时，则能看到 PRD、需求分析和一致性校验报告。
- AC-2: 给定设计阶段，当进入 `docs/03-solution/` 时，则能看到技术选型、系统架构、模块边界和接口设计文档。
- AC-3: 给定任何一条核心需求，当查阅追踪矩阵时，则能找到其对应的设计落点。

### `REQ-003` 保持 CLI-first 的统一执行入口

- 优先级：P0
- 描述：当前版本必须继续以 `Codex` / `Gemini CLI` 加 `factory-*` 命令为主要执行方式，而不是 API 平台。
- 用户故事：作为软件工厂使用者，我希望通过自然语言和统一命令入口推进工作，而不是记忆大量零散脚本。
- 前置条件：用户工作在本地 CLI 环境中。
- 业务规则：优先使用 `factory-dispatch`、`factory-agent-session`、`factory-command-profiles`、`factory-workflow-runner` 等高层入口。
- 依赖项：无。
- 排除范围：不包括 API 编排平台、Web 管理台或 SaaS 控制台。

验收标准：

- AC-1: 给定新用户，当阅读用户指南时，则能看到最值得记住的命令入口和常见使用场景。
- AC-2: 给定维护者，当阅读设计文档时，则能清楚当前版本为何采用 CLI-first。
- AC-3: 给定接口设计文档，当查看主要接口时，则能看到命令接口和文件契约，而非假设存在 HTTP API。

### `REQ-004` 明确人类文档与 AI 记忆分层

- 优先级：P0
- 描述：项目必须明确 `docs/` 与 `.factory/` 的职责边界，防止正式文档、AI 记忆和过程资产互相替代。
- 用户故事：作为维护者，我希望正式文档与 AI 记忆职责清晰，以便治理、审计和协作不混乱。
- 前置条件：项目存在运行时协议、控制面和人类说明文档。
- 业务规则：`docs/` 是正式人类文档，`.factory/` 是 AI 压缩记忆和过程资产；软件工厂项目的人类背景说明也应写回 `docs/`。
- 依赖项：`REQ-001`
- 排除范围：不要求当前仓库自己生成完整 `.factory/` 工作区。

验收标准：

- AC-1: 给定读者阅读 `docs/README.md` 时，则能清楚看到正式文档层与 AI 记忆层的分工说明。
- AC-2: 给定需求与设计文档时，则能找到关于双文档体系的明确表述。
- AC-3: 给定相关 skill 或配置入口时，则能看到 `docs/` 成为正式人类文档入口。

### `REQ-005` 支持角色化协作与交接理解

- 优先级：P1
- 描述：项目文档必须帮助不同角色理解谁负责什么、如何协作、何时交接。
- 用户故事：作为协作者，我希望知道需求、设计、实施和文档维护分别由谁承担，以便快速进入上下文。
- 前置条件：项目采用多角色协作模型。
- 业务规则：文档中应明确角色、职责和关键责任边界。
- 依赖项：`REQ-002`
- 排除范围：不要求本轮补齐全部角色工作台和交接模板。

验收标准：

- AC-1: 给定项目章程和需求分析文档，则能看到关键角色和职责说明。
- AC-2: 给定系统架构和模块边界文档，则能区分文档层、规则层、命令层和状态层的责任。
- AC-3: 给定用户指南，则能看到项目协调者和普通使用者的典型操作路径。

### `REQ-006` 提供带自然语言速查表的用户使用文档

- 优先级：P0
- 描述：项目必须提供面向实际使用者的快速开始、自然语言速查表、常见任务和故障排查说明。
- 用户故事：作为第一次使用软件工厂的协作者，我希望只看用户指南就能启动项目、接手现有项目并知道遇到问题时先看哪里。
- 前置条件：已有统一命令入口和工作流约定。
- 业务规则：用户指南应使用自然语言示例和任务导向结构，而不是只罗列脚本名，并应覆盖新项目、历史项目纳管、需求、设计、开发、缺陷、变更、发布和交接等典型流程。
- 依赖项：`REQ-003`
- 排除范围：不要求图形界面或视频教程。

验收标准：

- AC-1: 给定首次使用者，当阅读用户指南时，则能看到可直接复制给 AI 的自然语言速查表。
- AC-2: 给定用户不确定下一步时，则用户指南应明确推荐 `agent-session` 和 `state-doctor` 一类入口。
- AC-3: 给定用户遇到常见问题，则用户指南应提供原因判断和处理方式。

### `REQ-007` 接管非软件工厂历史项目并完成纳管

- 优先级：P0
- 描述：当协作者接管一个已经开发完成、但不是用软件工厂完成的历史项目时，系统必须先基于真实实现状态建立当前基线，再把它纳入软件工厂治理，用于后续 Bug 修复和新增需求。
- 用户故事：作为接手历史项目的协作者，我希望 AI 先识别该项目当前真实状态，并补齐软件工厂所需的规则、文档和状态文件，以便后续维护都能纳入统一流程。
- 前置条件：项目已经存在代码、配置、运行方式、已有文档或发布结果，但尚未接入软件工厂。
- 业务规则：历史项目纳管前，应优先读取代码、配置、现有文档、最新发布结果和可用运行方式；纳管后，再以 `AGENTS.md`、`GEMINI.md`、`.factory/project.json`、`.factory/memory/current-state.md` 和正式 `docs/` 作为后续维护基线。
- 依赖项：`REQ-003`, `REQ-006`
- 排除范围：不要求自动修复所有历史不一致，只要求先识别当前真实状态并完成纳管基线。

验收标准：

- AC-1: 给定一个不是软件工厂项目的历史项目，当用户请求 AI 开始接手时，则用户指南中应明确给出“先纳管、后维护”的自然语言说法。
- AC-2: 给定历史项目还没有 `AGENTS.md`、`GEMINI.md` 和 `.factory/` 时，则 AI 应先基于代码、配置、现有文档和最新发布结果建立当前状态基线。
- AC-3: 给定历史项目已经完成纳管时，则后续 Bug 修复统一走 `BUG-*`，新增需求统一走 `CR-*` 与需求/设计更新流程。

## 4. 非功能需求

### `NFR-001` 可发现性

- 指标：新协作者在 10 分钟内能从 `docs/README.md` 定位项目定位、核心设计入口和用户指南。
- 约束：`docs/README.md` 必须包含推荐阅读路径和目录说明。
- 验证方式：人工走查。

### `NFR-002` 一致性

- 指标：核心正式文档 100% 带有更新时间和稳定引用关系；默认人类文档配置指向 `docs/`。
- 约束：需求、设计、使用说明和追踪矩阵之间必须可互相引用。
- 验证方式：文档检查与配置检查。

### `NFR-003` 可维护性

- 指标：首批正式文档全部采用单文件演进，并包含变更记录。
- 约束：避免新增 `v2`、`final` 等平行副本。
- 验证方式：目录与文件结构检查。

## 5. 关键流程

1. 维护者通过 `docs/README.md`、项目章程和 PRD 了解项目定位与边界。
2. 协作者通过系统架构、模块边界和接口设计理解 CLI-first 架构与关键命令入口。
3. 使用者通过用户指南完成初始化、接手项目、推进需求/设计等常见任务。
4. 接手历史项目时，协作者先完成项目纳管，再把后续 Bug 修复和新增需求纳入软件工厂流程。

## 6. 风险、假设与待确认问题

### 风险

- 文档与脚本后续演进不同步。
- 仍有旧配置或说明保留过期路径，导致读者误判正式入口。
- 当前接口以 CLI 和文件契约为主，若后续增加 HTTP API，需要补充新的契约文档。

### 假设

- 当前产品边界继续保持 CLI-first。
- 软件工厂项目本身的人类说明文档全部以 `docs/` 为准。

### 待确认

- 下一阶段是否补齐管理员指南、部署说明、发布说明和运维手册。
- 是否需要为文档同步建立自动检查或脚本化保障。
