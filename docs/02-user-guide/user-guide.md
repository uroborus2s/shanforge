# 用户指南

**产品/系统名称：** 山海工枢 / shanforge  
**版本：** v1.2  
**主要读者：** 最终用户 | 协作者 | 项目维护者  
**负责人：** 仓库维护者  
**关联 ID：** `REQ-003`, `REQ-005`, `REQ-006`, `REQ-007`, `API-001`, `API-002`, `API-006`, `API-007`  
**最后更新：** 2026-03-27

## 1. 产品简介

- 这个系统能做什么：
  - 帮助你在 `Codex` 或 `Gemini CLI` 中，以阶段化方式组织需求、设计、实施、测试、发布和交接。
  - 把正式人类文档、AI 记忆、工作项和项目状态统一到可追踪的软件工厂流程中。
- 适合谁使用：
  - 项目维护者
  - 项目协调者
  - 使用软件工厂流程推进业务项目的协作者
- 使用前准备：
  - 可使用 `Codex` 或 `Gemini CLI`
  - 可访问本仓库中的 `scripts/`、`skills/` 和 `docs/`
  - 在目标项目根目录工作时，具备读写项目文件的权限

## 2. 推荐的使用方式

当前最推荐的方式不是手动记忆全部 `factory-*` 脚本，而是：

1. 先让模型读取项目规则与当前状态。
2. 用自然语言描述你要做的事。
3. 由模型优先选择 `agent-session`、`dispatch`、`command-profiles` 或 `workflow-runner`。
4. 把结果落回 `docs/`、`.factory/memory/`、`.factory/workitems/` 和 `.factory/project.json`。

建议的自然语言前缀分两种：

- 已经纳入软件工厂的项目：
  `先读取 AGENTS.md / GEMINI.md、.factory/project.json、.factory/memory/agent-session.md、.factory/memory/current-state.md 和当前阶段文档，然后……`
- 还没有纳入软件工厂的历史项目：
  `先读取当前仓库代码、配置、现有文档、最新发布结果和可用运行方式，梳理项目当前真实状态；再把它升级到软件工厂结构，然后……`

如果你希望把当前仓库里的共享 skills 同时暴露给本地 `Codex` 和 `Gemini CLI`，可以直接运行：

`python3 scripts/sync-codex-skills`

默认行为：

- 从当前仓库的 `skills/` 目录读取共享 skills
- 增量同步到 `~/.codex/skills` 和 `~/.gemini/skills`
- 跳过 `.system` 一类隐藏目录
- 若目标目录已有同名项，则保留原项，并退回到 `shanforge-<skill>` 别名
- 若目标根目录是损坏的软链接，可显式加 `--repair-broken-target-links`

## 4. 历史项目纳管规则

这里的“旧项目”指的是一个已经开发完成、但从来没有接入过软件工厂的历史项目。

这类项目要分两步处理：

1. 先做“历史项目纳管”
2. 再做“软件工厂接手后的持续维护”

### 4.1 纳管前，以历史项目当前真实状态为准

在项目还没有 `AGENTS.md`、`GEMINI.md`、`.factory/` 和阶段化 `docs/` 之前，不要假设它已经具备软件工厂上下文。

这时推荐的事实优先级如下：

1. 当前源码、配置文件和构建方式
2. 当前已发布版本、部署结果或运行行为
3. 项目已有 README、设计文档、接口说明和运维文档
4. 最近的需求单、缺陷单、发布说明或变更记录
5. 用户补充的业务背景和维护目标

处理原则：

- 如果历史文档和当前实现不一致，以当前真实实现状态和最新发布结果为准。
- 如果发现冲突，先把冲突点告诉协作者，再决定如何建立基线。
- 历史项目接手的第一目标不是立刻编码，而是先建立“当前状态基线”。

### 4.2 纳管后，以软件工厂正式状态为准

当项目已经补齐 `AGENTS.md`、`GEMINI.md`、`docs/`、`.factory/project.json`、`.factory/memory/current-state.md` 之后，后续维护统一按软件工厂规则推进。

这时需要明确区分“协作入口”和“事实来源”。

协作入口：

- `AGENTS.md` / `GEMINI.md`
- 它们负责告诉 AI 先读什么、遵守什么、哪些边界不能越过
- 它们不应承载安装结果、测试通过情况、当天运行状态等易变事实

事实优先级：

1. `.factory/project.json`
2. `.factory/memory/current-state.md`
3. 当前阶段的正式 `docs/` 文档
4. 活跃的 `TASK-*`、`CR-*`、`BUG-*`
5. 最近执行记录、最近快照、最近发布/交接包
6. `AGENTS.md` / `GEMINI.md` 中仍然有效的稳定协作规则

后续规则：

- Bug 修复统一走 `BUG-*`。
- 新增需求或范围变化统一走 `CR-*`，必要时回到需求和设计文档更新。
- 代码、正式文档、测试和 `.factory/memory/` 必须同步更新。
- 如果 `AGENTS.md` / `GEMINI.md` 混入了“当前没有依赖”“锁文件失败”“今天构建不通过”这类结论，应把这些内容迁移到现状快照，再刷新顶层入口文档。

配套资料：

- [历史项目现状基线模板](../04-project-development/02-discovery/current-state-analysis.md)
- [历史项目纳管 checklist](../04-project-development/05-development-process/historical-project-onboarding-checklist.md)
- [历史项目标准提示词模板](./prompt-templates.md)
- [历史项目纳管自动化入口设计](../04-project-development/04-design/historical-project-onboarding-automation.md)

说明：

- checklist 和提示词模板可以立刻使用。
- 当前仓库已经提供历史项目纳管 MVP 命令，可直接执行：
  `factory-dispatch historical-project-onboarding --project <path> --owner <name> --goal "<goal>"`
- 如需简写，也可以使用：
  `factory-dispatch legacy-onboard --project <path> --owner <name> --goal "<goal>"`

推荐直接使用这句话：

`这是一个已经开发完成、但不是用软件工厂完成的历史项目。请先基于当前代码、配置、现有文档、最新发布结果和可用运行方式，梳理项目当前真实状态，建立软件工厂接手所需的 AGENTS.md、GEMINI.md、docs/ 和 .factory 基线；完成纳管后，后续 bug 修复统一走 BUG，新增需求统一走 CR，并以软件工厂的正式状态继续推进。`

## 5. 快速开始

1. 先阅读 [项目章程](../04-project-development/01-governance/project-charter.md) 和 [产品需求文档](../04-project-development/03-requirements/prd.md)，理解软件工厂是什么。
2. 如果项目已经纳入软件工厂，让模型先读取 `AGENTS.md` / `GEMINI.md`、`.factory/project.json`、`.factory/memory/agent-session.md`、`.factory/memory/current-state.md` 和当前阶段文档。
3. 如果项目还是历史项目，优先执行 `factory-dispatch historical-project-onboarding --project <path> --owner <name> --goal "<goal>"`，或先让 AI 基于代码、配置、现有文档和最新发布结果建立当前状态基线，再补齐软件工厂结构。
4. 如果你不确定下一步，优先运行或请求模型使用 `factory-agent-session` 和 `factory-state-doctor`。
5. 如果你已经知道要做什么，但不想记脚本名，优先使用 `factory-dispatch`。

## 6. 最值得记住的入口

| 页面/入口                    | 用途                                                        | 注意事项                                     |
| ---------------------------- | ----------------------------------------------------------- | -------------------------------------------- |
| `factory-agent-session`      | 生成会话卡，告诉你该读什么、当前卡在哪里、推荐下一步是什么  | 最适合接手项目或重新进入上下文               |
| `factory-dispatch`           | 统一动作分派入口                                            | 适合已经知道要做哪个动作，但不想记具体脚本名 |
| `factory-command-profiles`   | 运行高层场景入口，如需求启动、设计启动、日终收尾            | 适合典型流程而不是单动作                     |
| `factory-workflow-runner`    | 执行高层收尾，如 `pre_gate`、`daily_close`、`release_ready` | 适合阶段收口                                 |
| `factory-state-doctor`       | 诊断缺什么、卡在哪里、哪里没同步                            | 不确定当前状态时优先使用                     |
| `scripts/sync-codex-skills`  | 把仓库内共享 skills 增量同步到 `~/.codex/skills` 和 `~/.gemini/skills` | 适合统一本地 Codex / Gemini CLI 的共享 skills 入口 |
| `factory-agent-motivation`   | 刷新团队动能、自治预算和正向强化信号                        | 适合多人协作、长链路推进前校准节奏           |
| `factory-recovery-coach`     | 在阻塞、空转、证据不足或质量漂移时给出恢复方案              | 优先于重复试错或情绪化施压                   |
| `factory-pattern-fix`        | 把单点问题扩展为同类扫描和预防动作                          | 适合缺陷、返工和重复问题处理                 |
| `factory-evolution-baseline` | 把有效做法沉淀成项目默认基线                                | 适合阶段结束、问题关闭或策略升级后使用       |

## 7. 常用任务

### 任务 1：初始化一个新软件工厂项目

1. 在目标项目目录中准备项目名称、创意和技术栈描述。
2. 让模型调用 `factory-init`，创建 `docs/`、`.factory/` 和项目规则骨架。
3. 再启动需求和设计阶段，补齐 PRD、需求分析和设计文档。

预期结果：

- 项目内生成阶段化文档结构和基础状态文件。
- 你可以继续用自然语言推进需求、设计和任务拆解。

### 任务 2：接手一个已开发完成、但非软件工厂项目

1. 先让 AI 读取当前代码、配置、现有文档、最近发布结果和可用运行方式，建立项目当前真实状态基线。
2. 再为该项目补齐 `AGENTS.md`、`GEMINI.md`、`docs/`、`.factory/` 和当前阶段基线，让它正式纳入软件工厂。
3. 纳管完成后，用 `agent-session` 或 `state-doctor` 验证当前阶段、阻塞项和下一步。
4. 从这一刻起，后续 bug 修复统一走 `BUG-*`，新增需求统一走 `CR-*` 和需求/设计更新。

预期结果：

- 你能把一个历史项目正式切换到软件工厂维护模式。
- 后续维护不再依赖临时聊天和零散记录，而是依赖软件工厂正式状态。

### 任务 3：推进需求或设计阶段

1. 如果当前还在需求阶段，优先补齐 `prd.md`、`requirements-analysis.md` 和 `requirements-verification.md`。
2. 如果需求已确认，启动设计阶段并维护 `technical-selection.md`、`system-architecture.md`、`module-boundaries.md`、`api-design.md` 和 `ux-ui-design.md`。
3. 变更边界或需求时，不要直接跳实现，先回写正式文档。

预期结果：

- 后续实施、测试和交接都有稳定事实来源。

### 任务 4：推进实现并保持同步

1. 通过 `factory-dispatch`、`factory-command-profiles` 或具体 `factory-*` 命令推进工作项。
2. 代码类工作项进入 PR 流时，按 `pr-start -> pr-review -> pr-merge -> close-workitem` 闭环。
3. 每次重要变更后，同步更新代码、正式文档、测试和 `.factory/memory/`。

预期结果：

- 项目状态、正式文档和 AI 记忆保持一致。

### 任务 5：在多人协作里维持积极性和自主性

1. 在协作启动、阶段切换或节奏变弱时，运行 `factory-agent-motivation`。
2. 如果任务卡住、原地打转、证据不足或质量漂移，优先运行 `factory-recovery-coach`。
3. 如果修复的是一个重复问题，优先运行 `factory-pattern-fix`，扩大到同类扫描。
4. 当本轮形成了明确有效的做法，再运行 `factory-evolution-baseline` 沉淀基线。

预期结果：

- 团队保持高主动性，但不会越过审批和事实边界。
- 知识能沉淀到项目基线，而不是只停留在单次会话里。

## 8. 关键使用规则

- 不跳阶段。需求未确认前不进入设计，设计未确认前不进入正式实现。
- `docs/` 是给人看的正式文档，`.factory/` 是给 AI 压缩读取和过程控制的资产。
- 如果不确定下一步，优先使用 `agent-session` 和 `state-doctor`，而不是盲目执行底层脚本。
- 当需求或设计边界发生实质变化时，优先建 `CR-*` 或更新正式文档，不要只改代码。
- 高主动性不等于越权。需要主动推进、主动补证据、主动扩大同类检查，但不能绕过审批、PR、Gate 和正式事实。
- 历史项目纳管前，以当前真实实现状态和最新发布结果为准。
- 历史项目纳管后，以软件工厂生成的正式状态为准。

## 9. 常见问题

| 问题                                                  | 原因                     | 处理方法                                                                                                |
| ----------------------------------------------------- | ------------------------ | ------------------------------------------------------------------------------------------------------- |
| 我不知道应该先读什么                                  | 当前阶段或项目状态不清晰 | 先生成 `agent-session`，再看推荐阅读                                                                    |
| 我在接手一个历史项目，它还没有 `.factory/` 和规则文件 | 项目还没纳入软件工厂     | 先以代码、配置、现有文档和最新发布结果建立当前状态基线，再补齐软件工厂结构                              |
| 历史项目已经纳管，但旧文档和当前状态对不上            | 纳管后状态没有同步       | 以 `.factory/project.json`、`.factory/memory/current-state.md` 和当前阶段正式文档为准，并让 AI 列出冲突 |
| 我只记得大概目标，不记得脚本名                        | 命令入口过多             | 优先使用 `factory-dispatch`                                                                             |
| 文档很多，不知道哪个是正式的                          | 入口层和记忆层混淆       | 以 `docs/` 为正式入口，以 `.factory/memory/` 为 AI 压缩入口                                             |
| 我改了实现，但不确定还要改什么                        | 变更同步面不明确         | 至少同步代码、`docs/`、测试和 `.factory/memory/`                                                        |
