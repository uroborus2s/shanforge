# 历史项目纳管 Checklist

**文档状态：** 已建立基线  
**主要读者：** 项目协调者 | 架构师 | 维护者  
**负责人：** 历史项目纳管负责人  
**关联 ID：** `REQ-007`, `TASK-005`  
**最后更新：** 2026-03-27  

## 1. 适用范围

本清单用于一个已经开发完成、但从来没有按软件工厂结构治理的历史项目。

目标不是“重做项目”，而是把它纳入软件工厂，让后续 Bug 修复、需求变更和版本维护都能走统一流程。

## 2. 使用方式

- 每次纳管按顺序执行
- 没完成上一组动作，不进入下一组
- 每完成一项，都要留下证据或产物
- 如发现历史文档与当前实现冲突，以当前真实实现和最新发布状态为准

## 3. 阶段清单

### A. 建立当前状态基线

- [ ] 确认仓库路径、默认分支、当前负责人和目标维护范围
- [ ] 确认项目当前是否可运行、如何构建、如何测试、如何部署
- [ ] 确认最新发布版本、最近一次部署结果和当前线上状态
- [ ] 盘点已有 README、需求文档、设计文档、接口文档和运维文档
- [ ] 记录当前已知缺陷、技术债和高优先级新增需求
- [ ] 产出或更新 [历史项目现状基线模板](/Users/uroborus/shanforge/docs/01-discovery/current-state-analysis.md) 对应内容

退出标准：

- 你能用一句话说明“这个项目现在真实是什么状态”
- 你知道后续是先修 Bug、先补文档，还是先做需求变更

### B. 补齐软件工厂治理骨架

- [ ] 在项目根目录补齐 `AGENTS.md`
- [ ] 在项目根目录补齐 `GEMINI.md`
- [ ] 创建 `docs/` 基础目录
- [ ] 创建 `.factory/` 基础目录
- [ ] 初始化 `.factory/project.json`
- [ ] 明确项目当前阶段，推荐默认设为 `MAINTENANCE`

退出标准：

- 项目已经具备软件工厂最小治理骨架
- 后续可以生成 `agent-session`、`state-doctor` 等软件工厂产物

### C. 建立正式文档基线

- [ ] 创建项目章程或纳管说明，说明这次接手的范围和目标
- [ ] 把现有交付能力整理进 PRD 或需求现状文档
- [ ] 把当前实现方式整理进技术选型、系统架构和模块边界文档
- [ ] 明确哪些内容是现状事实，哪些是后续待改造项
- [ ] 明确后续 Bug、CR、TASK 的进入规则

退出标准：

- 人类可以通过 `docs/` 理解项目当前事实与后续维护方式

### D. 建立软件工厂接手后的首批动作

- [ ] 如果当前有线上缺陷，创建首批 `BUG-*`
- [ ] 如果当前有新增需求，创建首批 `CR-*`
- [ ] 如果需要补工程治理，创建 `TASK-*`
- [ ] 生成一次 `agent-session`
- [ ] 生成一次 `state-doctor`
- [ ] 确认当前阶段、阻塞项和下一步建议

退出标准：

- 软件工厂已经可以继续接手这个项目的后续维护

### E. 验证纳管是否完成

- [ ] 确认 Bug 修复后会同步代码、测试、正式文档和 `.factory/memory/`
- [ ] 确认新增需求会走 `CR-*` 与需求/设计更新
- [ ] 确认后续协作者知道以什么文档和状态为准
- [ ] 确认存在可直接复用的提示词模板

退出标准：

- 项目已从“历史项目”切换为“软件工厂维护项目”

## 4. 纳管完成后的最低交付物

- `AGENTS.md`
- `GEMINI.md`
- `docs/`
- `.factory/project.json`
- `.factory/memory/current-state.md`
- 一次 `agent-session`
- 一次 `state-doctor`
- 至少一个首批 `BUG-*`、`CR-*` 或 `TASK-*`

## 5. 不建议的做法

- 还没建立现状基线就直接大改代码
- 只补 `.factory/`，不补正式 `docs/`
- 只靠聊天结论，不留下正式纳管产物
- 把历史项目直接当成“新项目初始化”
- 跳过需求/设计回写，直接用 Bug 修复或功能开发代替纳管
