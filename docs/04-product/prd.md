## 1. 产品定义

Shanforge 是运行在 Codex、Gemini CLI 等代理宿主中的 `skill-first` 软件工厂资产。
它由 `using-shanforge`、专项 skills、正式文档、测试和 `.factory/` 项目事实组成。

Shanforge 不提供仓内 `src/` 平台运行时、模型网关、数据库、公共 API、SDK 或独立服务。
目标项目只保存自己的代码、文档、测试和 `.factory/` 事实，不依赖 Shanforge 源码路径、
虚拟环境或本机绝对路径。

## 2. 用户与目标

### 2.1 主要用户

- 项目负责人：批准产品边界、风险接受和不可逆业务选择。
- 工程协作者：使用专项 skill 完成需求、设计、实现、测试、评审和交付。
- 代理宿主：加载 skills，提供模型、工具、权限、沙箱和会话能力。
- Skill 维护者：维护流程合同、确定性脚本、测试和文档。

### 2.2 产品目标

- 用一条可审计控制链把自然语言请求转为可验收工程交付。
- 让简单任务走最短安全路径，让复杂任务具备完整设计、计划、Gate 和证据。
- 让正式事实、执行事实和恢复摘要各有唯一 owner。
- 让当前工作区与只含 Git 跟踪文件的环境可使用同一命令验证。
- 让用户所选主会话统一设计和分级，为每个子任务独立选择模型及推理强度，子代理只执行明确授权的任务包。

### 2.3 非目标

- 不实现独立 Agent 平台或模型服务。
- 不在目标项目安装 Shanforge 运行时依赖。
- 不把缓存、HTML、索引或 memory 摘要提升为正式产品事实。
- 不以模型判断替代人工风险接受、远端授权或生产审批。

## 3. 事实源

| 事实 | 唯一 owner | 说明 |
|---|---|---|
| 稳定产品、需求、设计、测试和交付规则 | `docs/` | 面向人类审计的正式基线 |
| 任务身份、状态、证据和 Gate | `.factory/workitems/*/ledger.jsonl` | 追加式执行事实 |
| 会话恢复与当前投影 | `.factory/memory/` | 有界摘要，不覆盖 docs 或 ledger |
| 可重建页面、索引和缓存 | 所属 skill 的输出目录 | 仅投影，可删除重建 |
| 目标项目代码与配置 | 目标项目仓库 | 不依赖 Shanforge 源码 |

发生冲突时，先回源该事实 owner 修正，再同步索引和 memory；禁止通过复制第二份“当前事实”解决冲突。

## 4. 功能需求

### REQ-SF-001：唯一流程控制面

`using-shanforge` 必须先判断请求是否影响项目，再决定是否恢复项目事实并选择唯一下一步 skill。

- AC-1：无项目影响时执行 `direct_handoff_without_project_restore`。
- AC-2：项目化请求按
  `classify_processing_mode_from_current_message` →
  `restore_current_facts [projectized]` → routing → scoping → executing → verifying。
- AC-3：工作 skill 只返回本职结果、证据和 needs，不自行选择前后置 skill。

### REQ-SF-002：全生命周期专项交付

需求、架构、接口、UI、计划、实现、测试、评审、提交、发布和运维必须由相应专项 skill
在用户授权范围内完成。

- AC-1：任务的需求、设计、实现和测试产物可通过 ID 或路径追踪。
- AC-2：Review 不能替代 verification；verification 不能替代人工确认。
- AC-3：简单局部任务不强制生成项目级计划或逐任务 review。
- AC-4：跨模块、高风险或多交付物任务必须有 task brief、计划和集中质量门。

### REQ-SF-003：项目事实与恢复

- AC-1：正式文档只保存稳定事实，ledger 只追加执行事件，memory 保持有界。
- AC-2：当前态只显示活动任务、阻塞、Gate、最近事实和唯一下一动作。
- AC-3：会话恢复不得默认全文读取 docs、archive 或大型 JSONL。
- AC-4：事实冲突必须修复 owner，不能用摘要掩盖。

### REQ-SF-004：验证与干净环境

- AC-1：每个非平凡实现至少有一个会在逻辑破坏时失败的测试。
- AC-2：交付候选必须通过完整 pytest、根 Ruff、JSON/JSONL 校验和 `git diff --check`。
- AC-3：本地提交后必须从该提交创建只含 Git 跟踪文件的干净环境，并使用同一正式命令通过。
- AC-4：计划、占位符或进行中结果不得写成完成。

### REQ-SF-005：Artifact 最小留存

- AC-1：Git 只保留正式文档、源码、测试、schema、小型 manifest、TaskCard、最小 ledger、
  最终 review、当前验证和必要 fixture。
- AC-2：大型候选、全量机器 payload、原始日志、截图和多轮 review 过程材料不进入 Git。
- AC-3：破坏性清理前保存可恢复备份，并登记清单、哈希和恢复校验。
- AC-4：已被正式基线取代的过程材料按时清理，不用 `.gitignore` 假装工作区已收口。

### REQ-SF-006：Skill 本地确定性能力

- AC-1：可重复辅助能力放在所属 skill 的 `scripts/`。
- AC-2：脚本优先使用标准库，从参数接收目标项目根目录。
- AC-3：仓库级 `scripts/` 只承载同步工具，不成为软件工厂流程主控。
- AC-4：Skill、入口或目录变化必须同步用户指南和测试。

### REQ-SF-007：只读项目快照

- AC-1：`using-shanforge` 可从目标项目 `.factory/` 生成只读 HTML 快照。
- AC-2：输入未变化时复用缓存；非法 JSON/JSONL 或关系图失败关闭。
- AC-3：快照不提供编辑、审批、提交或发布入口。
- AC-4：工作项数量不等于产品功能完成率，缺证据时显示不可计算。

### REQ-SF-008：主会话与动态子任务选档

- AC-1：用户所选主会话是总体设计、任务复杂度/风险分级、模型路由和失败升级的唯一 owner。
- AC-2：按 [子任务模型决策表](../../skills/using-shanforge/SKILL.md#子任务模型决策表) 为每个子任务独立选择满足需求的最低模型/推理强度，记录 `reasoning_demand`、`capability_source` 和选档理由；不得继承父会话配置。
- AC-3：worker 执行精确授权写集；analyst 仅在已有项目身份和父阶段内只读分析、不写文件或改变父阶段；独立 reviewer 不得由实现者自批。普通直接回答不创建项目身份或 ledger、不强制派发。
- AC-4：派发显式传入模型、effort、`fork_turns=none`，核对当前宿主能力和 role 固定值。配置文件与官网能力不作为已加载角色或派发证明，回执只证明宿主接受请求；Ultra 不作普通子任务默认 effort。
- AC-5：子代理不得重新分级、自授权扩 scope、自批 review 或自批项目完成。连续两次验证失败先补复现/证据、收窄任务；输入冲突、风险、范围或阶段变化交还主会话重评。
- AC-6：能力、角色或回执异常时失败关闭。父会话可在原授权范围内显式重选满足质量/风险下限的受支持组合；改模型、强度或角色须新派发并保留旧回执，不得用 `followup_task` 改配置、静默降级或代写 worker / 代替 reviewer。

### REQ-SF-009：权限与外部动作

- AC-1：只读诊断和已授权范围内的正常实现步骤可直接执行。
- AC-2：破坏性操作必须解析精确目标并优先可恢复。
- AC-3：push、PR、merge、部署、生产修改、凭证和不可逆业务动作必须有明确授权。
- AC-4：模型等级不能扩大用户授权、工具权限或项目写入边界。

## 5. 非功能需求

| ID | 要求 | 度量 |
|---|---|---|
| `NFR-SF-001` | 可复现 | 干净环境同命令全绿 |
| `NFR-SF-002` | 可审计 | 任务状态、review、verification 和 Gate 可回源 |
| `NFR-SF-003` | 最小化 | 无新增平台运行时、服务、数据库或依赖 |
| `NFR-SF-004` | 安全 | 未授权远端与生产动作数量为 0 |
| `NFR-SF-005` | 可维护 | 当前态 ≤80 行；专业 Skill 合同不被控制面重写 |
| `NFR-SF-006` | 可访问 | 项目快照 390px/1440px 无页面级横向溢出，主要入口可键盘访问 |

## 6. 当前交付顺序

1. 统一正式事实和项目恢复摘要。
2. 清理历史过程资产并完成工作区验证。
3. 形成 T01 本地基线提交，从该提交执行干净环境复验。
4. 由用户所选主会话固化任务分级、路由包和升级合同。
5. 验证动态选档、显式派发、只读边界及失败重派，子代理只能执行授权任务。
6. 集中 review、完整验证、本地提交并保持工作区干净。
