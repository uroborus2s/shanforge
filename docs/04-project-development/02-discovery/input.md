# 项目输入

**项目名称：** 山海工枢 / shanforge  
**负责人：** 仓库维护者  
**主要读者：** 产品 | 需求分析 | 架构 | 项目经理  
**下游输出：** 头脑风暴记录 | 项目章程 | PRD  
**最后更新：** 2026-03-27  

## 1. 原始创意

- 建设一套可约束、可追踪、可协作、可持续演进的软件工程 Agent / 软件工厂体系。
- 这套体系运行在 `Codex` 和 `Gemini CLI` 上，通过共享 rules、skills 和 `factory-*` 脚本组织需求、设计、实施、测试、发布和交接。
- 需要增加 `docs/` 文件夹，把面向人类阅读的需求规划、设计说明和用户使用文档整理出来。

## 2. 启动原因

- 当前仓库已经具备脚本、skills 和合并版工作流说明，但项目正式的人类文档入口不够清晰。
- 新协作者需要花较多时间在代码、脚本和长文档之间来回切换，理解项目成本偏高。
- 需要把“产品是什么、怎么设计、怎么使用”沉淀到稳定的正式文档中。

## 3. 预期技术栈或实施边界

- 当前运行模式：CLI-first
- 宿主环境：`Codex` / `Gemini CLI`
- 主要实现形态：Python 脚本、Markdown 文档、JSON 配置、共享 skills
- 当前不以 API 平台、浏览器管理台或云端部署为主要交付目标

## 4. 已知约束

- 时间：本轮先补齐最小可用人类文档包，不一次性铺满所有阶段文档。
- 资源：在现有仓库结构内完成，不新增复杂生成系统。
- 合规/安全：保留人类文档与 AI 记忆分层，避免把 `.factory/` 当正式审计资产。

## 5. 当前最想确认的问题

- 当前仓库的正式人类文档入口应如何组织。
- 需求规划、设计文档与用户使用说明的边界如何划分。
- `docs/` 建成后，默认配置和 skill 说明是否也要同步切换。
