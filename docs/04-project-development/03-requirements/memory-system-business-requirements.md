## 1. 文档目标

本文档不讨论底层算法细节，而是回答记忆系统在业务层必须解决的几个问题：

- 启动一个会话时，系统到底该加载哪部分长期记忆。
- 为什么前端项目、Rust 后端项目、漫剧项目不能长期共用一个记忆池。
- 一个混合技术栈项目同时用 Rust 和 TypeScript 时，记忆和能力应该如何组织。
- `skill` 在系统里扮演什么角色，它与长期记忆的边界是什么。
- 多角色、多 Agent 协作时，记忆、技能和任务流如何串起来。

## 2. 已达成的业务共识

- 会话的底层运行引擎可以统一，但每次会话装配进去的内容不应统一。
- 长期记忆默认不应把前端、Rust、漫剧等明显不同生产线的经验混在一个池子里。
- 项目规则不是长期记忆，项目规则属于当前工作现场，应由当前目录下的规则文件承载。
- `skill` 不是事实记忆，而是流程记忆或方法包，解决“怎么做”，不是“记住什么”。
- 混合技术栈项目不应按语言拆成多个长期记忆脑子，而应按项目形成一套共享长期记忆，再按需加载多个 `skill`。
- 会话档案、长期记忆、项目规则、技能包、子 Agent 结果必须分层管理，不能混成一个概念。

## 3. 业务角色与典型场景

| 角色 | 典型场景 | 关键诉求 |
|---|---|---|
| 前端项目负责人 | 启动 Web/移动端前端项目会话 | 希望系统优先记住 UI、交互、组件、移动端相关长期经验 |
| Rust 后端负责人 | 启动服务端或基础设施项目会话 | 希望系统优先记住 Cargo、模块边界、性能、安全相关长期经验 |
| 漫剧制作协作者 | 启动剧本、分镜、角色设定项目会话 | 希望系统优先记住角色设定、镜头节奏、脚本产出流程 |
| 全栈项目负责人 | 启动同时包含 Rust 与 TypeScript 的单一产品项目 | 希望项目共用一套长期记忆，但可按需调用前后端不同技能 |
| 平台维护者 | 规划多 Profile、多 Skill、多 Agent 协作方式 | 希望知道系统如何防止记忆污染、如何选择装配入口 |

## 4. 业务分层模型

| 层次 | 业务含义 | 解决的问题 | 默认加载方式 | 不该承载什么 |
|---|---|---|---|---|
| Profile 级长期记忆 | 这个“长期脑子”已经学会了什么 | 长期偏好、稳定经验、通用约定 | 启动会话时按入口直接加载 | 全量会话日志、临时调试细节 |
| 项目规则 | 当前仓库或当前现场怎么做事 | 当前项目的约束、目录、命令、交付标准 | 按当前工作目录读取规则文件 | 跨项目通用经验 |
| Skill 索引与 Skill 正文 | 解决某类任务的方法包 | 前端改版、Rust 重构、文档写作、漫剧分镜等流程 | 启动时给索引，正文按需加载 | 项目长期事实、用户长期偏好 |
| 会话档案 | 这次具体聊了什么、做了什么 | 可回放、可检索、可压缩 | 自动留档 | 不应全部进入长期记忆 |
| 子 Agent 汇总 | 临时专员完成了一段任务后的结果 | 主 Agent 汇总、决策、继续执行 | 任务完成后回传摘要 | 不应直接替代主会话长期记忆 |

## 5. 启动与装配原则

### 5.1 会话不是“自动猜脑子”，而是“先选入口，再装配内容”

业务上应明确承认：系统不能只靠当前目录自动判断应该加载哪套长期记忆。当前目录更适合决定“当前项目规则”，而不是决定“长期脑子是谁”。

因此，启动一个会话时需要先确定：

- 这次进入哪个 `profile`
- 该 `profile` 自带哪套长期记忆、人格和技能集合
- 当前工作目录下还要叠加哪份项目规则

### 5.2 当前目录负责“现场规则”，不是“长期脑路由”

从不同目录启动会影响：

- 当前默认工作路径
- 项目规则文件的发现与加载
- 相对路径、命令执行和文件操作的默认现场

但它不应默认决定：

- 要切到哪套长期记忆桶
- 要混入哪些跨项目长期经验

## 6. 关键业务需求

### `MEM-BIZ-001` 会话启动必须能路由到正确的长期记忆域

- 优先级：P0
- 描述：系统必须支持通过显式入口选择长期记忆域，而不是把所有生产线经验都放入一个共享脑子。
- 用户故事：作为平台使用者，我希望一开始就进入正确的长期脑子，而不是先开聊再发现记忆拿错。
- 业务规则：长期记忆域的选择优先由 `profile` 或等价入口决定；当前目录只补充项目规则，不负责长期记忆分桶。

验收标准：

- AC-1: 给定 `frontend`、`rust`、`anime` 三类入口，则系统可加载三套不同的长期记忆。
- AC-2: 给定同一台机器上的多个 `profile`，它们的长期记忆、会话档案、技能和配置互相隔离。
- AC-3: 给定错误入口启动，则系统能明确暴露当前 `profile`，便于用户纠正，而不是静默混用。

### `MEM-BIZ-002` 不同生产线的长期记忆必须隔离，避免污染

- 优先级：P0
- 描述：系统必须支持将前端、Rust 后端、漫剧等明显不同生产线的长期经验分开维护。
- 用户故事：作为长期并行处理多类工作的使用者，我不希望 UI 经验污染后端会话，也不希望创作流程污染工程会话。
- 业务规则：长期记忆应优先按“生产线或长期职责”拆分，而不是默认全局共池。

验收标准：

- AC-1: 给定前端长期记忆中包含 `pnpm`、组件库、移动端适配等经验，它们不会默认出现在 Rust 或漫剧会话中。
- AC-2: 给定 Rust 长期记忆中包含 Cargo、错误处理、性能经验，它们不会默认出现在前端或漫剧会话中。
- AC-3: 给定漫剧长期记忆中包含人物设定、分镜节奏、提示词流程，它们不会默认干扰工程类会话。

### `MEM-BIZ-003` 混合技术栈项目必须支持“单项目长期记忆 + 多技能按需加载”

- 优先级：P0
- 描述：对于同一个产品同时使用 Rust 与 TypeScript 的场景，系统必须允许一个项目共用一套长期记忆，同时按需调用多个技术栈的 `skill`。
- 用户故事：作为全栈项目负责人，我希望同一产品的上下文是一体的，而不是被语言边界强行切裂。
- 业务规则：混合项目优先按项目建长期记忆域，而不是按语言拆多个脑子。

验收标准：

- AC-1: 给定同一个仓库同时包含 Rust 后端和 TypeScript 前端，则系统可在同一长期记忆域下工作。
- AC-2: 给定当前任务只涉及前端，则只加载前端相关 `skill`；只涉及后端，则只加载后端相关 `skill`。
- AC-3: 给定一次任务横跨前后端，则系统可以同时加载多个 `skill`，或拆成多个子 Agent 并行处理。

### `MEM-BIZ-004` `skill` 必须作为流程记忆按需加载，而不是全量常驻

- 优先级：P0
- 描述：系统必须在新会话启动时提供 `skill` 索引，但不应把所有 `skill` 正文全量塞入上下文；`skill` 正文应按需加载或由用户显式预加载。
- 用户故事：作为平台维护者，我希望系统既能知道有哪些方法包，又不因一次性加载全部技能而浪费上下文。
- 业务规则：启动时放索引，执行时按任务加载正文；用户通过 `/skill` 或预加载参数可强制装载特定 `skill`。

验收标准：

- AC-1: 给定一个新会话，系统会先暴露可用 `skill` 索引，而不是所有 `skill` 正文。
- AC-2: 给定任务与某个 `skill` 相关，模型可主动拉取该 `skill` 正文进入当前上下文。
- AC-3: 给定用户显式指定某个 `skill`，系统会在会话开始或指令触发时直接装载该 `skill`。

### `MEM-BIZ-005` 长期记忆必须自动维护，但保持小而精

- 优先级：P0
- 描述：系统必须支持自动沉淀长期记忆，但只能保存稳定、可复用、跨会话有价值的内容。
- 用户故事：作为使用者，我希望系统越用越懂我和我的项目，但不会把所有临时过程都塞进长期脑子。
- 业务规则：长期记忆应自动做新增、替换、删除和合并；需要长度预算和清理策略。

验收标准：

- AC-1: 给定用户长期偏好、项目长期约定或稳定踩坑结论，则系统可自动沉淀到长期记忆。
- AC-2: 给定临时调试日志、一次性路径、会话中间过程，则默认不进入长期记忆。
- AC-3: 给定长期记忆空间接近上限，则系统优先合并、替换或移除过时条目，而不是无限增长。

### `MEM-BIZ-006` 会话档案必须与长期记忆分层，防止“全量日志误当记忆”

- 优先级：P0
- 描述：系统必须把“这次做过什么”的完整档案与“以后都要记得什么”的长期记忆分开存放。
- 用户故事：作为协作者，我既希望未来能回查历史细节，也不希望每次新会话都背着一大堆旧日志。
- 业务规则：会话档案负责全量留档和搜索；长期记忆只负责高度浓缩后的稳定结论。

验收标准：

- AC-1: 给定一次长会话，完整过程会进入会话档案，而不是全部进入长期记忆。
- AC-2: 给定后续需要回查历史细节，系统可通过会话搜索或历史摘要召回，而不是依赖长期记忆承载。
- AC-3: 给定当前会话过长，则系统优先压缩和摘要当前上下文，而不是扩张长期记忆体积。

### `MEM-BIZ-007` 多角色、多 Agent 协作必须由主 Agent 串联，子 Agent 不直接拥有全局脑

- 优先级：P1
- 描述：系统必须支持主 Agent 拆分任务、派发子 Agent、回收摘要并继续执行；子 Agent 默认应作为临时专员，而不是独立修改全局长期记忆。
- 用户故事：作为项目负责人，我希望系统能把研究、实现、校验分工协作，但主控链条保持清晰。
- 业务规则：主 Agent 负责拆任务和收口；子 Agent 负责局部执行和摘要回传；长期记忆回写默认由主 Agent 决定。

验收标准：

- AC-1: 给定一个复杂任务，主 Agent 可拆成多个子任务并行执行。
- AC-2: 给定子 Agent 完成任务，其输出默认以摘要形式回到主会话，而不是直接污染共享长期记忆。
- AC-3: 给定主 Agent 判断子任务结果具有长期价值，主 Agent 才会将其沉淀到长期记忆或流程技能中。

### `MEM-BIZ-008` 记忆系统必须对“当前装配了什么”保持可解释

- 优先级：P1
- 描述：系统必须让使用者知道当前会话到底装配了哪套长期记忆、哪些项目规则、哪些 `skill` 和哪些子 Agent 结果。
- 用户故事：作为平台维护者，我希望记忆系统的行为可解释，而不是一旦答错就不知道错在路由、记忆、技能还是会话污染。
- 业务规则：系统至少要能暴露当前 `profile`、当前工作目录、已加载项目规则、已加载 `skill` 和长期记忆来源。

验收标准：

- AC-1: 给定一个会话，使用者可以明确知道当前处于哪个 `profile`。
- AC-2: 给定 `skill` 被加载，系统可追踪是“用户显式指定”还是“模型按需加载”。
- AC-3: 给定记忆召回错误，平台维护者可判断是记忆分桶错误、项目规则错误还是 `skill` 装配错误。

## 7. 分桶与装配策略

### 7.1 推荐的长期记忆拆分策略

| 场景 | 推荐策略 | 说明 |
|---|---|---|
| 同时长期做前端、Rust、漫剧三条线 | 按生产线拆 `profile` | 避免三类长期经验互相污染 |
| 同一产品是全栈混合项目 | 按项目拆 `profile` | 一个项目脑子，多个技术 `skill` 按需组合 |
| 单一生产线下的短周期小项目 | 复用生产线 `profile` + 项目规则 | 不必为每个小项目都建独立长期脑子 |
| 超长期、保密或术语密集项目 | 单独项目 `profile` | 强隔离、强沉淀、强可控 |

### 7.2 三个典型业务例子

- 前端项目：使用 `frontend` 长期记忆域，叠加当前仓库规则，按需加载 React、UI、设计系统相关 `skill`。
- Rust 后端项目：使用 `rust` 长期记忆域，叠加当前仓库规则，按需加载 Cargo、测试、架构重构相关 `skill`。
- 漫剧项目：使用 `anime` 长期记忆域，叠加当前项目的角色设定与产出规则，按需加载剧本、分镜、提示词流程相关 `skill`。

### 7.3 混合技术栈项目例子

同一个产品若同时包含 Rust 与 TypeScript：

- 长期记忆以“项目”为单位组织。
- Rust 与 TypeScript 只是该项目内部的两套工作方法，不应拆成两个长期脑子。
- 当前任务只改前端时，只加载前端 `skill`。
- 当前任务只改后端时，只加载 Rust `skill`。
- 当前任务横跨两端时，同时装载两套 `skill`，或拆给两个子 Agent。

## 8. 明确排除项

- 不要求系统只靠当前工作目录自动推断长期记忆桶。
- 不要求每做一个项目都默认生成一套新的长期记忆。
- 不要求所有 `skill` 在每次会话启动时全文加载。
- 不要求子 Agent 默认直接改写共享长期记忆。
- 不要求长期记忆承载完整历史日志或完整项目档案。

## 9. 成功指标

| 指标 | 目标 | 观测方式 |
|---|---|---|
| 记忆相关性 | 不同生产线会话中的无关记忆显著减少 | 真实会话抽检 |
| 启动正确率 | 使用者可稳定进入正确长期记忆域 | Profile 使用统计与回访 |
| Skill 效率 | 新会话只带索引，正文按需加载 | 会话上下文抽样 |
| 混合栈适配能力 | 同一项目可在单脑模型下完成前后端协作 | 全栈样例项目演练 |
| 协作可控性 | 子 Agent 结果可被主 Agent 汇总而不污染全局脑 | 多 Agent 任务演练 |
