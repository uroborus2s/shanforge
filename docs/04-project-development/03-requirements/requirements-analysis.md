# 需求分析文档

**项目名称：** 山海工枢 / shanforge  
**文档状态：** 已确认基线  
**负责人：** 仓库维护者  
**主要读者：** 架构 | 开发 | 测试 | 项目经理  
**上游输入：** 头脑风暴记录 | PRD | 当前 `docs/` 正式文档体系  
**下游输出：** 架构设计 | 实施计划 | 测试策略  
**关联 ID：** `REQ-001` ~ `REQ-007`, `NFR-001` ~ `NFR-003`, `RISK-001` ~ `RISK-003`  
**最后更新：** 2026-03-27  

## 1. 分析目标

- 这份文档要解决什么判断问题：判断当前软件工厂仓库的人类文档基线应该覆盖哪些内容、优先顺序如何，以及它们对后续设计和维护意味着什么。
- 这份文档输出给谁使用：给维护者、架构设计者和后续协作者，用于理解为什么要先补齐 `docs/` 以及如何控制范围。

## 2. 核心流程拆解

| 流程 | 关联需求 | 关键参与者 | 风险点 |
|---|---|---|---|
| 固化正式文档入口 | `REQ-001`, `REQ-004` | 仓库维护者、项目协调者 | 旧路径和新路径并存导致入口混乱 |
| 整理需求与设计基线 | `REQ-002`, `REQ-005` | 产品、架构、维护者 | 文档结构过大或过空 |
| 维持 CLI-first 使用路径 | `REQ-003`, `REQ-006` | 使用者、维护者 | 用户仍需记忆过多脚本细节 |
| 纳管历史项目并建立维护基线 | `REQ-007` | 接手协作者、项目协调者 | 错把过期说明当事实，或未建立纳管基线就开始维护 |

## 5. 关键约束

- 业务约束：本轮任务目标是建立首批正式文档，而不是重构整套软件工厂实现。
- 数据约束：当前接口大量依赖 Markdown、JSON 配置和本地文件路径，文档必须贴近这些真实事实。
- 性能/容量约束：当前项目主要是本地 CLI 运行，不以高并发服务为目标。
- 集成约束：默认配置、skill 说明和文档入口需要保持一致，否则新文档难以真正被使用。

## 6. 对设计与测试的影响

- 对架构的影响：需要把现有仓库解释为“文档层、规则层、命令层、状态层”协作的结构，而不是单一脚本集合。
- 对接口设计的影响：接口文档要覆盖 CLI 命令和文件契约，而不是假设当前已经存在 REST API。
- 对测试策略的影响：本轮更适合做文档和引用一致性检查，并重点检查历史项目纳管场景下“纳管前/纳管后”事实来源是否表达清晰。

## 7. 未决问题与建议

- 建议下一阶段补充管理员指南、部署/发布文档，形成更完整的人类交付包。
- 建议未来增加一个“文档入口一致性检查”，避免配置和 skill 继续引用过期路径。
- 建议未来增加一个“历史项目纳管检查”，在读取项目时主动识别缺失的规则文件、状态文件和基线文档。
- 与软件工厂项目本身直接相关的人类说明文档已经应当收敛到 `docs/`，不再继续保留 `workflows/` 副本。
