**项目名称：** 山海工枢 / shanforge
**文档状态：** `v2` 需求分析基线
**负责人：** 仓库维护者
**主要读者：** 产品 | 架构 | 平台开发 | 测试
**上游输入：** PRD | Hermes Agent 源码调研报告
**下游输出：** 系统架构 | 模块边界 | API 设计 | 实施计划
**关联 ID：** `REQ-001` ~ `REQ-010`, `NFR-001` ~ `NFR-005`
**最后更新：** 2026-04-13

## 1. 分析目标

本分析文档用于回答三个问题：

- `v2` 为什么必须被当作新产品，而不是旧工作流的续写。
- 新需求集之间的依赖顺序是什么。
- 哪些需求是首轮必须落地的最小平台内核。

## 2. 需求主题归类

| 主题 | 关联需求 | 价值 | 主要风险 |
|---|---|---|---|
| 平台核心内核 | `REQ-001`, `REQ-006`, `REQ-009` | 建立统一主循环、会话和标准输出 | 运行时边界不清导致平台变成概念壳 |
| 业务隔离与装配 | `REQ-002`, `REQ-003`, `REQ-010` | 让业务只面向 manifest、workflow 和模板开发 | 业务装配路径不顺，开发者仍回到硬编码 |
| 大模型抽象 | `REQ-004` | 支持不同 workflow / step 选择不同模型 | 模型选择逻辑下沉到业务层 |
| 能力治理 | `REQ-005`, `REQ-007` | 工具、风险、审批和执行具备统一边界 | 未注册调用和越界执行再次出现 |
| 扩展与协作 | `REQ-008` | 支撑多入口和多代理扩展 | 委派和入口适配与主内核产生分叉 |

| `REQ-005` | `REQ-001` | Capability Registry 是运行时调用基础 |
| `REQ-006` | `REQ-001` | Session 和 Context 是主循环基础设施 |
| `REQ-007` | `REQ-005`, `REQ-006` | 审批和执行要基于能力信息与会话状态 |

## 4. 优先级判断

| 需求 | 优先级 | 原因 |
|---|---|---|
| `REQ-001` | P0 | 没有内核，后续抽象都无承载点 |
| `REQ-002` | P0 | 不先隔离业务，平台仍会被业务耦合污染 |
| `REQ-003` | P0 | Workflow DSL 是业务装配的核心入口 |
| `REQ-004` | P0 | 大模型是平台基础能力，必须先抽象 |
| `REQ-005` | P0 | 没有 capability 契约就无法安全执行 |
| `REQ-006` | P0 | 上下文和会话是 Agent 运行的必要条件 |
| `REQ-007` | P0 | 不先收口风险边界，平台无法进入可控实施 |
| `REQ-008` | P1 | 多入口与多代理重要，但可在内核稳固后推进 |
| `REQ-009` | P0 | 不统一响应，平台对上层不可用 |
| `REQ-010` | P0 | 用户价值来自快速装配业务流，而不是抽象本身 |

## 5. 关键设计结论

### 5.1 `v2` 的产品中心必须转移

`v2` 的产品中心不再是命令、脚本、文档迁移或历史项目接管，而是一个可复用的 Agent 平台内核。旧资产如果继续出现在主需求中，会把平台目标重新拉回工具集合和流程治理，这与用户当前方向冲突。

### 5.2 业务开发面必须上移

如果业务流仍需要直接理解底层模型调用、脚本入口和执行控制，则平台没有真正成立。因此 `REQ-002`、`REQ-003` 和 `REQ-010` 是业务价值闭环的核心组合。

### 5.3 大模型交互必须被当作基础设施

用户已经明确提出“大模型是最核心的基础”，但这不意味着业务层直接依赖大模型 SDK。正确分层是：

- 业务层声明意图、workflow 和输出契约。
- 模型层通过 `ModelPolicy` 表达选择策略。
- 运行时通过 `LLM Runtime + LLMProviderPort` 完成真正调用。

### 5.4 Workflow DSL 是平台采用门槛的决定因素

如果 Workflow DSL 过于底层，用户无法快速构建业务流；如果过于宽泛，运行时会失去稳定性。因此 DSL 必须优先聚焦：

- `step`
- `uses`
- `model_policy`
- `approval`
- `output_schema`
- `retry/fallback`

## 6. 风险分析

| 风险 | 影响 | 缓解措施 |
|---|---|---|
| 平台设计过宽 | 推迟首轮实现 | 先锁定最小核心契约，再扩展可选能力 |
| DSL 不稳定 | 业务装配难以复用 | 先做最小 schema，并用 demo app 校验 |
| Provider 抽象失效 | 业务重新耦合 SDK | 强制业务层只引用 `model_policy` |
| Capability 不收口 | 出现逃逸调用 | 所有执行入口都走 registry 与 policy |
| 记忆层膨胀 | 上下文失控 | 先做最小 context package 与 evidence 回写规则 |

## 7. 建议的最小实现顺序

1. `REQ-001` Agent Platform Kernel
2. `REQ-002` Agent App Manifest
3. `REQ-003` Workflow DSL
4. `REQ-004` ModelPolicy + LLM Runtime
5. `REQ-005` Capability Registry
6. `REQ-006` Session / Context / Memory
7. `REQ-007` Approval / Sandbox
8. `REQ-009` AgentResponse
9. `REQ-010` Demo App / Template / Local Simulation
10. `REQ-008` Delegation / Gateway / Multi-entry

## 8. 结论

`v2` 的正确方向不是“继续维护旧工作流并补一点 Agent 能力”，而是“以 Hermes 的核心思想为输入，重建一个对业务友好的抽象 Agent 平台”。需求集必须围绕平台内核、业务装配、多模型解耦、能力治理和证据闭环展开；旧版本叙事不再参与需求判断。
