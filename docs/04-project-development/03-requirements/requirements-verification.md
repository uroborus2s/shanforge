## 3. 一致性检查

| 检查项 | 结果 | 说明 |
|---|---|---|
| 产品目标是否单一 | 通过 | 所有需求都围绕抽象 Agent 平台建设 |
| 是否存在旧平台继承需求 | 通过 | 旧版本诉求不再出现在需求集合中 |
| 业务与平台是否分层 | 通过 | `REQ-002` 明确 Agent App 与平台内核隔离 |
| 大模型交互是否解耦 | 通过 | `REQ-004` 明确 `ModelPolicy + LLM Runtime + LLMProviderPort` |
| 工作流装配是否可落地 | 通过 | `REQ-003` 和 `REQ-010` 形成业务装配闭环 |
| 执行边界是否可控 | 通过 | `REQ-005`, `REQ-007`, `REQ-009` 共同覆盖 capability、审批、响应与证据 |

## 4. 残留风险

- 首轮实现若只完成抽象而无 demo Agent App，会影响 `REQ-010` 的验证价值。
- 若 Workflow DSL 和 ModelPolicy schema 设计失衡，后续契约可能需要回调。
- 多入口和多代理扩展虽然是 `P1`，但其接口边界必须在架构期先定义。

## 5. 对下游设计的约束

- 系统架构必须围绕平台内核、业务 App、workflow、模型运行时、能力注册和治理控制面展开。
- 模块边界必须禁止业务层直接依赖基础设施适配器。
- API 设计必须以平台内部契约为主，而不是以命令列表为主。
- 实施计划必须从领域模型、契约和运行时主循环起步，而不是从遗留流程迁移起步。
