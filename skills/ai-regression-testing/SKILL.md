# AI 回归测试

用于 AI 代理改代码后的回归防线。主目标是证明“这类 Bug 不会再出现”，不是追求覆盖率数字，也不是替代人工设计判断。

## 何时启用

- AI 修改了 API、服务、数据映射、状态管理或权限逻辑。
- 修复了一个 Bug，需要防止同类问题再次出现。
- 同一行为存在多条路径：真实路径、沙盒路径、模拟路径、特性开关、缓存路径。
- 代码评审可能被同一假设误导，需要自动化断言兜住。

## 核心风险

AI 常见失败不是语法错误，而是“修了一条路径，漏了另一条路径”。典型风险：

- 响应字段、状态码或错误格式在不同路径不一致。
- 数据查询、映射、schema 和返回契约没有同步。
- UI 错误状态、乐观更新或缓存没有回滚。
- 用默认值、空结果、宽松解析或静默异常掩盖根因。

## Bug 根因修复门槛

回归测试不是为兜底方案背书，而是证明同一个根因不会再次出现。每个 Bug 修复必须先满足以下条件：

1. 有失败复现：测试、命令、日志、截图或最小输入能稳定展示原始问题。
2. 有根因说明：区分直接原因和根源原因，说明问题为什么发生、为什么此前没有被测试或契约拦住。
3. 有根因修复：修改造成问题的真实代码路径、契约或数据流，不只是在出口处补默认值。
4. 有防回归断言：测试断言根因路径已经被修复，并覆盖相关多路径一致性。

禁止把以下做法当作 Bug 修复完成标准：

- 捕获异常后返回空结果、默认成功或静默忽略。
- 字段缺失时临时填默认值，却不修复上游 SELECT、映射、schema 或契约。
- 增加重试、宽松解析、宽泛兼容分支，却没有证明失败原因是瞬态或格式兼容问题。
- 只修沙盒路径或只修真实路径，让另一条路径继续漂移。

兜底、降级和兼容分支只有在已经是产品契约、可观测、可测试、且根因已修复或风险被明确接受时才允许保留。

## 默认流程

1. 提取 Bug 指纹：输入、路径、失败输出、受影响契约。
2. 找出同一行为的所有路径：真实、沙盒、模拟、缓存、特性开关。
3. 写最小回归断言，优先在修复前看到失败。
4. 修根因路径，不用出口兜底替代上游修复。
5. 验证多路径契约一致：字段、状态码、错误格式、权限、状态迁移。
6. 把测试命名为它防住的 Bug 或契约，方便后续定位。

## 风险分级验证

- 低风险：单路径纯逻辑。运行目标单元测试。
- 中风险：API、状态、缓存、沙盒/真实双路径。运行目标集成测试和契约断言。
- 高风险：权限、支付、删除、数据迁移、公共 API、多服务契约。运行相关集成测试和目标 E2E；不扩大到无关端到端套件。

不要为从未出过问题、也没有风险信号的区域铺测试。测试应随 Bug 和高风险契约自然增长。

## 与相邻 workflow 的边界

- 根因不明时先做系统化调试，只能加诊断或复现测试。
- TDD 负责新行为的红绿循环；本 skill 负责 AI 容易漏掉的回归和多路径一致性。
- 完成声明前必须用新鲜命令证明回归测试通过。

## 应当 / 禁止

应当：

- 发现 Bug 后尽量先写失败测试。
- 断言外部契约和用户可见行为，不断言无关实现细节。
- 让沙盒、模拟和真实路径返回同一契约。
- 记录直接原因、根源原因、修复点和防回归测试。

禁止：

- 根因未明时用兜底、默认值、静默异常或宽松兼容声明修复完成。
- 信任 AI 自评替代自动化测试。
- 在单元测试足以覆盖根因时硬写集成测试。
- 追求覆盖率百分比而忽略真实回归风险。
