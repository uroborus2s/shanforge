# 文档协同创作

用于把用户的零散上下文整理成能被目标读者理解的文档。它不是模板库，也不是流程总控；正式生命周期文档、固定目录和模板优先交给 `document-templates`，需求条目优先交给 `requirements-engineering`。

## 何时使用

- 用户要写、改、合并、精炼或评审文档、提案、RFC、设计说明、决策记录、项目说明。
- 用户有大量背景但结构不清，需要共同梳理目标读者、论点、章节和措辞。
- 文档需要反复迭代，以便让不在上下文里的读者也能理解。

## 不使用

- 用户只要一个简短回复、邮件或单段文案；直接回答即可。
- 已有明确模板和产物目录，且任务是生成标准项目文档；改用 `document-templates`。
- 任务核心是需求拆解、验收标准或用户故事；改用 `requirements-engineering`。
- 用户明确要求快速自由写作时，不强制套完整协作流程。

## 工作方式

1. 先问最少必要问题：文档类型、目标读者、期望影响、格式约束、已知事实来源。
2. 用户已有材料时先读材料，再指出缺口；不要让用户重复提供已在文件里的内容。
3. 先给结构，再逐段起草或修改；小改用局部编辑，不整篇重写。
4. 保留事实和不确定性边界；没有来源的内容标注为待确认，不编造。
5. 接近完成时做读者视角检查：读者会问什么、哪些假设没写、是否有矛盾或冗余。

## 输出契约

完成时回写：

- `status`: `done` 或 `blocked`
- `outputs`: 文档路径、章节草稿、修订摘要或评审意见
- `evidence`: 输入文件、用户确认、引用来源、关键决策和检查记录
- `verification`: 通读结果、结构检查、事实/链接检查、模板符合性；未运行要说明原因
- `needs`: 仍需确认的事实、受众、语气、审批人或发布位置

本技能只回写文档工作状态，不替 `using-shanforge` 决定下一步 skill。

## 验证要求

- 文档必须说明目标读者、目的和读者读完后的预期动作。
- 重要事实、链接、接口、日期、承诺和结论必须可追溯；无法核实则标注待确认。
- 最终交付前至少通读一次，删掉重复、口号化和无法支撑的句子。

## Blocked 语义

只有缺少关键事实且无法合理占位时才返回 `blocked`，例如目标读者未知、事实来源不可访问、用户要求引用但未给来源、现有文档冲突无法判断。`blocked` 必须列出缺口、已完成部分和继续所需的最小输入。
