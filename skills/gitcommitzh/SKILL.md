# Git 中文提交

用于把当前 Git 变更整理成一份可审阅的中文提交说明，并在范围清晰后执行本地提交。

## Slash 直接调用规则

- 当用户直接输入 `/gitcommitzh`，或消息以 `/gitcommitzh` 开头时，禁止把该输入解释为“展示 skill 定义”或“确认已读取 skill”。
- 当用户直接输入 `/gitcommitzh` 且没有附加参数时，必须立即执行默认工作流：
  - 先读取 `git status --short`、`git diff --stat`、`git diff --cached --stat`
  - 然后输出结构化中文变更说明和中文提交信息草案
  - 默认停在“说明 + commit message 草案”阶段，不直接执行 `git commit`
- 当用户使用 `/gitcommitzh` 且同一条消息中明确包含“提交”“commit”“执行提交”等意图时，才允许在范围明确后继续执行本地 `git add -- <files>` 与 `git commit`
- 当用户同一条消息中明确包含“提交”“commit”“执行提交”等意图时，这本身就构成执行授权；禁止在没有具体阻塞原因的情况下只输出说明而不执行提交
- 当用户明确要求提交、当前暂存区为空、且用户没有指定文件子集时，默认自动执行 `git add .` 纳入当前工作区改动，而不是因为“暂存区为空”中止
- 禁止在 `/gitcommitzh` 直调场景下只回复“已收到 skill”“如果你需要再告诉我”之类的占位话术
- 如果当前仓库没有任何可提交改动，必须明确返回“当前没有可提交的 Git 变化”，而不是停在 skill 确认阶段

## 适用场景

- 用户要求你总结当前 Git 改动并提交。
- 用户要求你写中文提交说明、中文 commit message 或结构化变更摘要。
- 用户已经做完改动，希望你帮他完成本地 `git add` + `git commit`。
- 用户希望先看清当前改动，再决定是否提交。

## 可直接触发的中文示例

- `请先总结当前 git 改动，再帮我写中文提交说明并提交。`
- `把这次 diff 整理成结构化中文变更说明，然后执行本地 commit。`
- `先看暂存区和工作区改动，告诉我这次提交范围，再用中文 commit message 提交。`
- `只提交这几个文件：src/api.ts、tests/api.test.ts。请先总结变更，再提交到 git。`
- `帮我检查当前改动能不能组成一个 commit；如果可以，生成中文提交标题和正文并提交。`
- `直接用 /gitcommitzh 帮我整理这次提交。`

## 不适用场景

- 用户只要远端发布、推送或建 PR。
- 用户要改写历史，例如 `commit --amend`、`rebase`、`squash`、强推。
- 用户没有要求提交，只是普通代码解释或代码评审。

遇到这些场景时，改用更合适的 GitHub / 发布工作流，不要强行使用本 skill 收尾。

## 核心目标

1. 先看清 Git 变更范围，而不是直接提交。
2. 先给出结构化中文说明，再执行提交。
3. 保证一次提交只表达一个清晰主题。
4. 避免把不相关改动、临时文件或未经核实的结果写进提交。

## 参考资料

- [中文提交模板](references/chinese-commit-patterns.md)

在生成提交标题和正文时，优先参考这份模板里的类型建议、正文结构和反例。

## 默认工作流

### 第 1 步：审查提交范围

至少读取下面这些信息：

- `git status --short`
- `git diff --stat`
- `git diff --cached --stat`
- 必要时读取：
  - `git diff --cached`
  - `git diff`
  - `git diff --name-only`
  - `git log --oneline -5`

审查规则：

- 如果已经有暂存区改动，默认把“已暂存集合”视为本次提交候选范围。
- 如果同时存在未暂存或未追踪文件，必须明确说明哪些会进入本次提交，哪些不会进入。
- 如果没有暂存区改动，再从工作区中识别本次任务相关文件。
- 如果用户明确要求提交、暂存区为空、且没有指定文件子集，则默认把当前工作区全部改动视为本次提交候选范围，并进入自动 `git add .`。
- 如果改动明显分成多个无关主题，停止自动提交，要求用户拆分范围或明确指定本次提交只包含哪一组文件。

### 第 2 步：生成结构化中文说明

在提交前，先输出一份结构化中文说明。默认结构如下：

#### 提交范围

- 本次提交覆盖哪些文件或模块
- 哪些文件已暂存，哪些文件被排除

#### 变更概览

- 用 2 到 5 条中文完整句说明这次提交解决了什么问题
- 说明本次变更属于 `feat` / `fix` / `refactor` / `docs` / `test` / `chore` 中的哪一类

#### 详细改动

- 按文件或按主题分组描述
- 每组至少说清：
  - 改了什么
  - 为什么改
  - 行为上有什么变化

#### 风险与影响

- 是否影响已有行为、接口、配置、脚本或文档
- 是否存在未验证风险

#### 验证情况

- 只写真实执行过的验证
- 如果没有跑测试或验证不完整，要明确写“未执行”或“只做了部分验证”

#### 提交信息

- 提交标题
- 提交正文
- 最终写入 Git 的提交信息原文

禁止把这份说明写成一句模糊的总结。要让阅读者不打开 diff，也能大致明白本次提交做了什么。
如果后续要执行 `git commit`，这里生成的“提交标题 + 提交正文”就是最终提交消息源；禁止在执行提交时临时改写成另一套内容。
如果用户要求直接提交，必须在提交前显式输出一段“最终写入 Git 的提交信息原文”，作为唯一允许写入 Git 的文本源。

### 第 3 步：生成提交标题与正文

先观察最近提交风格：

- 如果仓库已有稳定格式，优先沿用。
- 如果看不出稳定格式，默认使用：
  - 标题：`<type>: <中文简短标题>`
  - 例如：`fix: 修正历史项目纳管文档的人机入口边界`

如需更具体的中文措辞、类型选取或正文模板，读取 [中文提交模板](references/chinese-commit-patterns.md)。

标题要求：

- 简短、可扫读
- 准确描述本次提交的核心动作
- 不要堆太多并列事项

正文要求：

- 使用中文
- 采用分段或项目符号
- 至少覆盖：
  - 背景或目的
  - 主要改动
  - 验证情况

如果用户已经明确给了 commit 标题或风格要求，优先服从用户要求。

提交消息一致性规则：

- 如果已经在“结构化中文说明”里生成了 `提交标题` 和 `提交正文`，执行 `git commit` 时必须原样复用这份标题和正文。
- 禁止在真正执行提交时重新概括、临时缩写、偷换措辞或改成另一套 message。
- 提交前回复里展示给用户的标题和正文，与最终写入 Git 的标题和正文必须一致。
- 如果你决定调整标题或正文，必须先更新结构化中文说明，再执行提交；禁止“说明一套、提交另一套”。
- 如果用户要求直接提交，必须先输出 `最终写入 Git 的提交信息原文` 区块，再执行 `git commit`。
- `最终写入 Git 的提交信息原文` 区块里的内容必须包含完整标题和完整正文，禁止只给标题、只给摘要或只给正文要点。
- 执行 `git commit` 时，只能复用该区块中的原文；禁止提交时再次自由生成。
- 如果用户已经明确要求“提交 / commit”，且你已经给出明确的提交范围、最终提交标题、最终提交正文，则必须继续执行提交；禁止停在“状态：未提交”。

### 第 4 步：执行本地提交

执行规则：

- 如果已经明确了文件子集，或暂存区中已有候选集合，则只对本次确认纳入的文件执行 `git add -- <files>`
- 如果用户明确要求提交、暂存区为空、且没有指定文件子集，则默认自动执行 `git add .` 纳入当前工作区改动
- 禁止在范围不清晰时直接使用 `git add .`
- 禁止默认使用 `git add -A` 或 `git commit -am` 这类会扩大纳入范围的命令
- 当已存在暂存区候选集合或用户指定了文件子集时，禁止再用 `git add .` 扩大提交范围
- 提交时使用非交互式命令
- 优先使用多段 `-m` 写入标题和正文
- 提交命令中的标题和正文，必须逐字对应前面已经展示给用户的 `提交标题` 与 `提交正文`
- 禁止把 `git add`、`git commit`、`git status` 用 `&&` 串成一条“展示型命令”来糊成一步；要按实际执行顺序分别运行，并确保每一步都符合已确认范围
- 如果已经输出 `最终写入 Git 的提交信息原文`，则 `git commit` 必须严格使用该原文中的标题和正文，不得增删任何词句
- 提交前先明确展示“将纳入提交的文件列表”和“最终写入 Git 的提交信息原文”，再执行 `git add -- <files>` 与 `git commit`
- 如果走的是“暂存区为空 -> 自动 `git add .`”路径，必须先在说明里明确写出“将使用 `git add .` 纳入当前工作区全部改动”，再执行
- 用户明确写出“提交 / commit”时，不需要再次等待二次确认；只要范围清晰且没有具体阻塞原因，就直接执行 `git add -- <files>` 与 `git commit`
- 如果最终没有执行提交，必须明确给出具体阻塞原因，例如：范围仍冲突、hook 失败、权限错误、工作区为空；禁止只写“未提交”而不解释原因

如果用户明确说“提交这些改动”“帮我 commit”，则在范围明确后直接提交。

如果用户只要求“总结改动”或“写提交说明”，则停在说明和 commit message，不执行 `git commit`。

### 第 5 步：提交后回报结果

提交成功后，补充输出：

- 提交哈希短号
- 最终提交标题
- 纳入提交的文件列表或统计
- 如果有未纳入的工作区改动，要明确提醒

必要时可读取：

- `git show --stat --summary --format=fuller HEAD -1`

## 禁止行为

- 禁止不看 diff 直接提交。
- 禁止把明显不相关的改动混进同一个 commit。
- 禁止编造“已测试”“已验证”之类的结论。
- 禁止默认执行 `git push`、创建 PR、同步远端。
- 禁止默认执行 `git commit --amend`、`rebase`、`reset --hard` 或其他改写历史操作。
- 禁止在存在暂存区时偷偷把额外未暂存改动一起塞进提交，除非用户明确要求。
- 禁止在“暂存区为空”之外的场景里把 `git add .` 当成兜底偷懒动作。
- 禁止“先生成一份中文说明，再用另一份自拟 message 提交”。
- 禁止为了省事把结构化说明压缩成一句标题后直接提交，导致正文信息没有进入 commit message。
- 禁止在用户已经明确要求“提交 / commit”、且不存在具体阻塞原因时，仍然停在摘要输出阶段不执行提交。

## 冲突与异常处理

- 如果没有任何可提交改动，明确告诉用户“当前没有可提交的 Git 变化”，并停止。
- 如果提交失败，原样说明失败原因，例如 hook、lint、test、权限或冲突，不要假装提交成功。
- 如果仓库里有大量与你当前任务无关的脏改动，先圈定本次提交范围，再决定是否提交。
- 如果你无法判断哪些文件属于同一主题，先停下来让用户确认，而不是赌一把提交。

## 输出模板

默认按下面结构给用户：

```md
## 提交范围
- ...

## 变更概览
- ...

## 详细改动
- `path/to/file`: ...

## 风险与验证
- 风险：...
- 验证：...

## 提交信息
- 类型：...
- 标题：...
- 正文：...

### 最终写入 Git 的提交信息原文
标题：
<最终标题原文>

正文：
<最终正文原文>

## 提交结果
- 状态：未提交 / 已提交
- 提交号：...
- 阻塞原因：若未提交则必填
```

如果已经完成提交，`提交结果` 必须写清最终 commit hash；如果还没提交，明确写出停下来的原因。
