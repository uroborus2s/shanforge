# Git 中文提交

用于把当前 Git 变更整理成一份可审阅的中文提交说明，并在范围清晰后执行本地提交。

## Slash 直接调用规则

- 当用户直接输入 `/gitcommitzh`，或消息以 `/gitcommitzh` 开头时，禁止把该输入解释为“展示 skill 定义”或“确认已读取 skill”。
- 当用户直接输入 `/gitcommitzh` 且没有附加参数时，必须立即执行默认工作流：
  - 先读取 `git status --short`、`git diff --stat`、`git diff --cached --stat`
  - 然后输出结构化中文变更说明和中文提交信息草案
  - 默认停在“说明 + commit message 草案”阶段，不直接执行 `git commit`
- 当用户使用 `/gitcommitzh` 且同一条消息中明确包含“提交”“commit”“执行提交”等意图时，视为已授权提交；范围清晰后必须在同一轮执行本地提交，必要时先执行 `git add -- <files>`
- 当用户明确要求提交、当前暂存区为空、且用户没有指定文件子集时，默认从工作区识别“当前任务相关改动”；不得因为暂存区为空中止，也不得直接扩大为 `git add .`
- 禁止在 `/gitcommitzh` 直调场景下只回复“已收到 skill”“如果你需要再告诉我”之类的占位话术
- 如果当前仓库没有任何可提交改动，必须明确返回“当前没有可提交的 Git 变化”，而不是停在 skill 确认阶段

## 授权与交付规则

- 当用户原始消息已经明确包含“提交”“commit”“执行提交”等意图时，必须在同一轮内完成：审查范围、生成提交说明、执行 `git commit`、校验真实 hash、回显最终提交信息。
- 禁止先交付“中间态摘要”或“待提交草案”，再等待用户下一轮重新授权提交。
- 禁止在提交尚未完成时输出 `提交结果` 区块。
- 只有在 `git commit` 与提交后校验都完成后，才允许输出最终的 `提交结果`。

## 适用场景

- 用户要求你总结当前 Git 改动并提交。
- 用户要求你写中文提交说明、中文 commit message 或结构化变更摘要。
- 用户已经做完改动，希望你帮他完成本地 `git add` + `git commit`。
- 用户希望先核查当前改动，再决定是否提交。

## 可直接触发的中文示例

- `请先总结当前 git 改动，再帮我写中文提交说明并提交。`
- `把这次 diff 整理成结构化中文变更说明，然后执行本地 commit。`
- `先看暂存区和工作区改动，告诉我这次提交范围，再用中文 commit message 提交。`
- `只提交这几个文件：src/api.ts、tests/api.test.ts。请先总结变更，再提交到 git。`
- `帮我检查当前改动能不能组成一个 commit；如果可以，生成中文提交标题和正文并提交。`
- `直接用 /gitcommitzh 帮我整理这次提交。`

## 不适用场景

- 用户只要远端发布、推送或建 PR。
- 用户要求创建、切换、删除分支，或要求设计分支 / PR 策略；应先转入对应分支 / PR 工作流，分支状态明确后再回来提交。
- 用户要改写历史，例如 `commit --amend`、`rebase`、`squash`、强推。
- 用户没有要求提交，只是普通代码解释或代码评审。

遇到这些场景时，改用更合适的 GitHub / 发布工作流；本 skill 不执行这些动作。

## 核心目标

1. 先核清 Git 变更范围，而不是直接提交。
2. 先给出结构化中文说明，再执行提交。
3. 保证一次提交只表达一个清晰主题。
4. 默认只提交当前任务的修改内容。
5. 避免把不相关改动、临时文件或未经核实的结果写进提交。
6. 把本地提交接到 Shanforge 的 review、evidence、memory sync 和 work item ledger 上。

## 提交范围总原则

- 默认按“当前任务的修改内容”提交，而不是按整个工作区提交。
- 当前任务范围来自：用户本轮要求、用户指定文件、当前计划项 / todo、以及 diff 中能明确归属同一任务的文件；已暂存集合只能作为候选参考，不得仅由暂存状态决定提交范围。
- 只纳入与当前任务直接相关的文件；无关脏改动、临时文件、生成物、个人配置和其他任务改动必须排除。
- 提交前，暂存区内容必须与本次任务范围一致；若暂存区含范围外文件，停止并要求用户确认处理方式。
- 如果工作区改动能清楚分成多个任务，停止自动提交，要求用户指定本次提交范围，或建议拆成多个 commit。
- 只有用户明确说“提交全部改动”，或你已确认工作区全部改动都属于同一任务，才允许把全部工作区改动纳入候选范围。
- `gitcommitzh` 只负责当前分支的本地提交。禁止在本 skill 内创建、切换、删除开发分支；若用户明确要求分支操作，先转入分支 / PR 工作流，分支状态明确后再回来提交。

## PR 闭环与提交前置检查

当提交属于 Shanforge work item 时，提交前必须先核对 [PR 闭环与提交检查清单](references/pr-closure-checklist.md)。

最小检查：

- work item ledger 已能说明当前任务状态、review 结论、verification evidence 和 memory sync。
- `.factory/memory/review-ledger.jsonl` 中的真实独立 review 记录已与 work item ledger 对齐。
- 若 ledger 或 review 显示 `pending_human_confirmation`，必须看到用户明确 `human_approved` 或同轮明确要求继续提交。
- 禁止把未确认的 reviewer approved 当作提交闭环依据；`approved` 只代表 reviewer 通过，不等于人工确认。
- 提交范围必须只包含当前任务相关代码、文档、测试和 `.factory/memory/` 同步文件。
- gitcommitzh 不负责创建、推送或合并 PR；它只做当前分支本地提交。
- 若需要远端 PR、push、merge 或分支动作，先转入对应 Git / GitHub 工作流，本 skill 不代办。

## 默认工作流

### 第 0 步：核对 work item 闭环状态

如果当前改动属于某个 work item，先读取：

- `.factory/workitems/<WORKITEM-ID>/ledger.jsonl`
- `.factory/memory/review-ledger.jsonl`
- `.factory/workitems/<WORKITEM-ID>/evidence/`
- `.factory/workitems/<WORKITEM-ID>/reports/`
- `.factory/workitems/<WORKITEM-ID>/reviews/`

检查项：

- review 结论是否来自真实独立 reviewer，或是否已明确登记为用户覆盖继续。
- verification evidence 是否是本轮新鲜证据。
- memory sync 是否覆盖代码、文档、测试和 `.factory/memory/`。
- `pending_human_confirmation` 是否已有人工确认或用户同轮明确授权提交。
- PR / 提交状态是否不会被本地 commit 伪装成远端 PR 已合并。

### 第 1 步：审查提交范围

至少读取下面这些信息：

- `git status --short`
- `git diff --stat`
- `git diff --cached --stat`
- 提交前必须读取本次纳入范围的实际 diff：
  - 已暂存候选：`git diff --cached -- <files>`
  - 未暂存候选：`git diff -- <files>`
- 必要时读取：
  - `git diff --cached`
  - `git diff`
  - `git diff --cached --name-only`
  - `git diff --name-only`
  - `git log --oneline -5`

审查规则：

- 如果已经有暂存区改动，默认把“已暂存集合”视为本次提交候选范围；仍需通过当前任务范围和内容级核查后才能提交。
- 如果暂存区改动明显包含多个无关任务，停止自动提交，要求用户拆分暂存范围或明确本次只提交哪一组。
- 如果同一文件同时存在 staged 与 unstaged diff：
  - 读取该路径的 cached 与 unstaged diff。
  - 默认只提交 staged 内容。
  - 判断 staged 内容是否属于本次任务，unstaged 内容是否应排除或需用户确认。
  - 除非用户明确要求纳入未暂存部分，禁止对该路径再次执行 `git add -- <path>`。
- 如果同时存在未暂存或未追踪文件，必须明确说明哪些属于当前任务、哪些进入本次提交、哪些排除。
- 如果要纳入未追踪文件，提交前必须读取文件内容或用等价方式生成可审阅 diff；执行 `git add -- <file>` 后，还必须读取 `git diff --cached -- <file>` 核查新增内容。
- 如果没有暂存区改动，再从工作区中识别当前任务相关文件。
- 如果用户明确要求提交、暂存区为空、且没有指定文件子集，先列出当前任务候选文件；范围清晰时用 `git add -- <明确文件列表>`，范围不清晰时停止并要求用户确认。
- 只有用户明确要求“提交全部改动”，或你已确认全部工作区改动都属于同一任务时，才允许使用 `git add .`，并且必须在提交前说明原因。
- 如果改动明显分成多个无关主题，停止自动提交，要求用户拆分范围或明确指定本次提交只包含哪一组文件。

### 第 2 步：生成结构化中文说明

在提交前，先输出一份结构化中文说明。默认结构如下：

#### 提交范围

- 本次提交覆盖哪些文件或模块
- 哪些文件已暂存，哪些文件被排除

#### 变更概览

- 用 2 到 5 条中文完整句说明这次提交解决了什么问题
- 说明本次变更属于 `feat` / `fix` / `refactor` / `docs` / `test` / `chore` 中的哪一类

#### 详细改动

- 按文件或按主题分组描述
- 每组至少说清：
  - 改了什么
  - 为什么改
  - 行为上有什么变化

#### 风险与影响

- 是否影响已有行为、接口、配置、脚本或文档
- 是否存在未验证风险

#### 验证情况

- 只写真实执行过的验证
- 如果没有跑测试或验证不完整，要明确写“未执行”或“只做了部分验证”

#### 提交信息

- 提交标题
- 提交正文
- 拟写入 Git 的提交信息原文

禁止把这份说明写成一句模糊总结。应使阅读者无需打开 diff，也能理解本次提交的范围、目的、风险和验证情况。
如果后续要执行 `git commit`，这里生成的“提交标题 + 提交正文”就是最终提交消息源；禁止在执行提交时临时改写。
只生成草案时使用“拟写入 Git 的提交信息原文”；直接提交时按第 3 步在提交前展示“最终写入 Git 的提交信息原文”，提交后在结果区块中同时展示提交前最终原文与 Git 实际回显。

### 第 3 步：生成提交标题与正文

先观察最近提交风格：

- 如果仓库已有稳定格式，优先沿用。
- 如果看不出稳定格式，默认使用：
  - 标题：`<type>: <中文简短标题>`
  - 例如：`fix: 修正历史项目纳管文档的人机入口边界`

如需更具体的中文措辞、类型选取或正文模板，读取 [中文提交模板](references/chinese-commit-patterns.md)。

标题要求：

- 简短、可扫读
- 准确描述本次提交的核心动作
- 避免堆叠多个并列事项

正文要求：

- 使用中文
- 采用分段或项目符号
- 至少覆盖：
  - 背景或目的
  - 主要改动
  - 验证情况

如果用户已经明确给了 commit 标题或风格要求，优先服从用户要求。

提交消息一致性规则：

- 结构化说明中的 `提交标题` 和 `提交正文` 是唯一 message 来源。
- 若执行提交，先输出完整的 `最终写入 Git 的提交信息原文`；该区块用于审计，不构成二次确认。
- 执行 `git commit` 前，最终原文必须已在对话中可见；禁止只在命令内部生成最终 message。
- `git commit` 必须逐字复用该区块中的标题和正文，禁止提交时重新概括、缩写或改写。
- 若调整标题或正文，先更新结构化说明和最终原文，再执行提交。
- 用户已授权提交且范围清晰时，禁止停在 message 草案或“状态：未提交”。

### 第 4 步：执行本地提交

执行规则：

- 如果已经明确了文件子集，则只对本次确认纳入的文件执行 `git add -- <files>`
- 如果暂存区中已有候选集合，完成任务范围和内容级核查后，直接提交 staged 原样内容；不得为重复确认而重新 `git add` 已暂存路径
- 如果暂存区为空且用户没有指定文件子集，则先识别当前任务相关文件，再执行 `git add -- <明确文件列表>`
- 如果用户明确要求提交、暂存区为空、且没有指定文件子集，不得默认执行 `git add .`；只有确认全部改动都属于同一任务，或用户明确要求“提交全部改动”时才允许
- 如果纳入未追踪文件，必须先读取其内容或可审阅 diff；暂存后再读取 `git diff --cached -- <file>`，确认新增内容属于本次任务。
- 提交前必须读取 `git diff --cached --name-only`，确认暂存区文件集合与本次任务范围一致；若多出范围外文件，停止提交并说明原因
- 如存在 staged + unstaged 风险，提交前必须读取相关 `git diff --cached -- <path>` 与 `git diff -- <path>`。
- 确认 staged 内容只包含本次任务范围。
- 确认 unstaged 内容应排除或需用户确认；若无法确认，停止提交并说明风险。
- 如果暂存区已有范围外文件，禁止自行 `git restore --staged`、`git reset` 或重排用户暂存区；先说明冲突并等待用户确认
- 禁止在范围不清晰时直接使用 `git add .`
- 禁止默认使用 `git add -A` 或 `git commit -am` 这类会扩大纳入范围的命令
- 当已存在暂存区候选集合或用户指定了文件子集时，禁止再用 `git add .` 扩大提交范围
- 禁止在本 skill 内创建、切换、删除开发分支；禁止执行 `git checkout -b`、`git switch -c`、`git branch -c`、`git checkout <branch>`、`git switch <branch>` 等分支变更命令
- 提交时使用非交互式命令
- 优先使用多段 `-m` 写入标题和正文
- 提交命令中的标题和正文，必须逐字对应前面已经展示给用户的 `提交标题` 与 `提交正文`
- 禁止把 `git add`、`git commit`、`git status` 用 `&&` 串成不可审计的一步；要按实际执行顺序分别运行，并确保每一步都符合已确认范围
- 如果已经输出 `最终写入 Git 的提交信息原文`，则 `git commit` 必须严格使用该原文中的标题和正文，不得增删任何词句
- 提交前先明确展示“将纳入提交的文件列表”，并按第 3 步展示最终原文，再在同一轮继续执行本地提交；需要更新暂存区时只用 `git add -- <files>`
- 如果确实走“允许使用 `git add .`”路径，必须先用 `git rev-parse --show-toplevel` 确认仓库根目录，并在仓库根目录执行；同时在说明里明确写出“为什么全部工作区改动都属于本次任务”
- 如果最终没有执行提交，必须明确给出具体阻塞原因，例如：范围仍冲突、hook 失败、权限错误、工作区为空；禁止只写“未提交”而不解释原因
- 执行 `git commit` 后，必须再读取真实的 commit hash；只有拿到真实 hash 之后，才允许把 `提交结果.状态` 写成“已提交”
- `提交结果.提交号` 必须是 Git 实际返回的短 hash，禁止使用占位文本、推测值或“正在执行提交”之类的中间状态

如果用户只要求“总结改动”或“写提交说明”，则停在说明和 commit message，不执行 `git commit`。

### 第 5 步：提交后回报结果

提交成功后，补充输出：

- 提交哈希短号
- 最终提交标题
- 最终提交正文
- Git 中实际写入的完整提交信息原文
- 纳入提交的文件列表或统计
- 如果有未纳入的工作区改动，要明确提醒

提交后回显规则：

- 提交成功后，必须回显 Git 中实际写入的完整提交标题和完整提交正文，不能只回 `hash`、标题或变更统计。
- 这份回显必须来自 Git 实际结果，而不是仅复述提交前准备的草案。
- 至少读取一次 `git log -1 --format=%B` 或等价命令，确认最终 message 后再返回给用户。
- 至少读取一次 `git rev-parse --short HEAD` 或等价命令，确认真实短 hash 后再返回给用户。
- 如果提交前展示的原文和 Git 实际写入的原文不一致，必须显式指出差异。
- 如果 `git commit` 尚未执行完成、命令失败、或还没有拿到真实 hash，禁止把状态写成“已提交”。

必要时可读取：

- `git show --stat --summary --format=fuller HEAD -1`
- `git log -1 --format=%B`
- `git rev-parse --short HEAD`

## 禁止行为

- 禁止不看 diff 直接提交。
- 禁止把明显不相关的改动混进同一个 commit。
- 禁止编造“已测试”“已验证”之类的结论。
- 禁止在本 skill 内创建、切换或删除开发分支；提交必须发生在当前分支。
- 禁止默认执行 `git push`、创建 PR、同步远端。
- 禁止默认执行 `git commit --amend`、`rebase`、`reset --hard` 或其他改写历史操作。
- 禁止绕过当前任务范围规则：包括纳入额外未暂存改动、提交范围外暂存文件、默认使用 `git add .`、或在 staged + unstaged 风险下重新 `git add` 同一路径。
- 禁止在未读取内容或可审阅 diff 的情况下提交未追踪文件。
- 禁止提交信息不一致：包括说明内容与实际提交信息不一致、只提交标题不提交正文、或提交时重新生成 message。
- 禁止提交成功后只返回 `hash`、标题或文件统计；必须回显完整提交正文。
- 禁止在尚未得到真实 commit hash 时，把状态写成“已提交”。
- 禁止把 `[正在执行提交...]`、`处理中`、`pending`、占位 hash 或其他中间态文本写进 `提交号` 字段。

## 冲突与异常处理

- 如果没有任何可提交改动，明确告诉用户“当前没有可提交的 Git 变化”，并停止。
- 如果提交失败，原样说明失败原因，例如 hook、lint、test、权限或冲突；禁止声明提交成功。
- 如果仓库里有大量与你当前任务无关的脏改动，先圈定本次提交范围，再决定是否提交。
- 如果你无法判断哪些文件属于同一主题，先停下来让用户确认，禁止推测提交范围。
- 如果当前分支不适合直接提交，不得自行创建开发分支；说明阻塞原因，等待用户指定分支策略或改用分支 / PR 工作流。
