# Ponytail、代码形状与设计规则

## 决策顺序

每次实现先按以下顺序选择，停在第一个能满足已确认需求的方案：

1. 复用项目已有代码和约定。
2. 使用 Go 标准库。
3. 使用项目已经锁定的依赖。
4. 写满足当前需求的最少新代码。
5. 只有前四项均无法满足，且新增依赖或抽象有当前需求依据、比直接代码更小且更安全时才允许采用。

不得为“以后可能需要”增加层、接口、配置项、扩展点或兼容分支。安全校验、超时、资源释放、事务回滚和优雅停机不是可删除的多余设计。

## 单次调用拆分

- 禁止把一段只在一个位置使用的连续流程提取成只调用一次的私有函数或方法，仅为了缩短调用方、写注释式函数名或制造“步骤感”。
- 提取前必须用 `rg`、`gopls references` 或调用层级确认调用点。只有一个调用点且没有稳定边界时，保留内联。
- 已存在的单次调用私有 helper 若没有独立契约、资源所有权或可复用行为，应内联删除。
- `main -> run` 这类进程生命周期边界、HTTP handler、接口契约方法和包对外构造函数不视为“为了排版拆分的 helper”，但必须确实拥有资源、协议或包职责；不得借此包装一次转发。
- 不得通过提取只调用一次的 helper 来隐藏复杂度。先简化条件、数据流和职责。

## 嵌套深度

- 普通业务函数的控制流嵌套目标不超过 2 层，硬上限为 3 层。
- 使用 guard clause、错误立即返回、`continue` 和清晰的 `switch` 保持 happy path 平直。
- 超过 3 层时先消除布尔组合、反转条件或缩小输入状态；禁止仅把深层代码搬进单次调用 helper。
- 函数 literal、callback、事务闭包和 goroutine 进入时计 1 层；`if`、`for`、`switch`、`select` 每进入一层再计 1 层，`case` 本身不重复计层。
- 不允许作者自行豁免硬上限。无法降到 3 层时停止实现并返回 `needs_user_input`，由用户明确决定是否改变约束。

## Go 式面向对象

Go 没有类继承。面向对象在这里表示让状态、行为和所有权靠近，而不是照搬 Java 分层：

- struct 持有自身不变量和资源，receiver method 维护该不变量。
- 优先组合和显式依赖，不使用继承模拟、全局 service locator 或万能 base type。
- interface 由消费方定义，只包含消费方需要的方法。
- 只有一个真实实现且没有外部边界替身需求时，不创建 interface；直接依赖具体类型。
- 不创建只转发调用的 `Manager`、`Service`、`Factory`、`Registry` 或 repository 层。
- repository 只在持久化查询、事务边界或替换数据源的真实需求存在时引入；禁止通用 base repository 和泛型 CRUD 包装。

## 设计模式采用门槛

设计模式必须对应已经出现的问题，且是当前最小解：

| 模式 | 允许条件 | 禁止用法 |
|---|---|---|
| Strategy | 至少两个真实算法需要在运行时选择 | 为单一实现预留接口 |
| Factory | 至少两个真实产品或构造分支，且调用方不应知道构造细节 | 包装一次 `New` 调用 |
| Adapter | 隔离一个真实外部协议或第三方 API | 为想象中的第二供应商预留兼容层 |
| Middleware / Decorator | 鉴权、日志、恢复等正交行为需要组合 | 把普通业务步骤改造成链式框架 |
| State | 存在明确状态、合法迁移和非法迁移 | 用类型数量代替简单 `switch` |
| Observer / Event | 一个事实已有多个独立消费者或必须异步解耦 | 为单一调用引入事件总线 |
| Functional Options | 已确认的可选参数较多，普通构造函数已难以正确使用 | 默认给每个构造函数加 options |

采用模式时，在代码或设计说明中写清：当前问题、至少两个真实变化点、为何直接代码不足。条件消失时删除模式。

## 禁止推测性回退与兼容扩张

- 禁止“主方案失败后再试另一个地址、驱动、provider、格式、环境变量名或旧字段”。
- 禁止吞掉解析、配置、数据库和下游错误后返回空对象、默认成功或部分结果。
- 禁止为未在需求和当前工程中出现的旧版本、旧 key、旧 JSON 字段、旧路径、旧数据库或旧 API 增加 dual-read、dual-write、alias 或 adapter。
- 禁止 catch-all 解码、宽松字段忽略和无边界重试；未知字段与非法值必须失败并给出可定位错误。
- fallback 只有在需求明确列出触发条件、行为边界、可观测信号和测试时才允许；未满足四项时直接失败。
- Consul 动态配置只允许保留已经验证并正在使用的快照；这不是尝试另一种配置来源。首次必需配置加载失败仍必须启动失败。
- 兼容面只覆盖项目锁定版本和批准的输入契约。需要扩张时先取得用户或契约 owner 的明确决定。

## Review 检查

- 是否能删除一个文件、类型、接口、配置项或依赖而不损失当前需求？
- 是否存在只调用一次、只做转发或只为命名步骤存在的 helper？
- 是否有超过 3 层的控制流，或用 helper 隐藏的深层控制流？
- interface 是否有至少两个真实实现，或明确的外部边界替身需求？
- 设计模式是否有当前问题和真实变化点，而不是“最佳实践”装饰？
- 是否出现未获批准的 fallback、alias、dual-read、dual-write、宽松解析或兼容 adapter？
- 删除这些代码后，安全、正确性、资源释放和可观测性是否仍完整？
