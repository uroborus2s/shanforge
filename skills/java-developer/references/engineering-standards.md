# 工程阶段与工作方式

Java 开发不是只看代码规范。先判断阶段，否则容易在需求没定时写实现，在根因不明时写兜底，在只需评审时顺手重构。

## 阶段规则

| 阶段 | 进入条件 | 必须检查 | 退出条件 |
|---|---|---|---|
| 需求 / 澄清 | 目标、用户、边界或验收不清 | 业务目标、输入输出、异常流程、权限、验收标准 | 需求可验收 |
| 技术设计 | 需求已清楚但实现路径未定 | 分层、API、数据、事务、安全、测试、文档影响 | 设计可执行 |
| 实现 | 需求和设计已足够明确 | 既有结构、可复用工具、最小代码、测试 | 测试通过 |
| Bug 修复 | 有失败、异常或用户报告 | 复现、直接原因、根源原因、影响范围 | 根因修复和回归测试 |
| 重构 | 行为不变，目标是删除重复或降低复杂度 | 行为边界、调用方、公共工具 owner | 行为验证通过 |
| Review | 用户要求评审或提交前检查 | Bug、风险、缺测试、过度抽象、文档偏差 | 给出可执行问题 |
| 文档 | 需要 README、开发说明、接口说明或变更记录 | 事实来源、读者、公开范围、示例命令 | 文档能指导使用或维护 |

## 工作方式区分

- 新功能：先确认需求和设计。不清楚时只问最少问题，不先写代码。
- Bug 修复：根因不清楚就交给 `systematic-debugging`。根因明确后才能实现。
- 重构：不改外部行为。能删除就删除，能复用就复用。
- 代码评审：先报问题，不顺手改代码，除非用户明确要求修复。
- 文档：只写真实代码事实、命令和约束，不写空泛原则。
- 工程规范：输出可执行规则、禁止项和 Review checklist，不写教程合集。

## 质量门

- 实现和重构必须有对应测试、构建或最小可运行检查。
- Bug 修复必须覆盖根因路径，不为 fallback 背书。
- Review 必须有文件、行号或明确代码位置。
- 文档必须能指向事实来源：代码、配置、命令、测试或已批准设计。
- 无法验证时只能说明未验证和风险，不得宣称完成。
