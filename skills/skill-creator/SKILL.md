# 技能创造器 (Skill Creator)

用于创建新技能并进行迭代改进的专用技能。

## 适用边界

适用于创建、改写、压缩、翻译、评审和评估 skill 本身。

不适用于：

- 普通业务功能实现。
- 只需要执行某个已有 skill 的场景。
- Shanforge 阶段路由、review gate、人工确认或本地提交。
- 没有明确目标能力、触发条件或使用者的泛 prompt 优化请求；此时先澄清目标。

## 强制原则：中文、闭环、隔离

这些规则适用于所有新建、改写、翻译、压缩和评审 skill。

- 所有项目内 skill 默认使用中文；工具名、命令名、路径、文件名、API 名和代码标识符保留原文。
- 用户可见文本必须中文；引用外部英文资料时，只保留必要专名，并用中文解释其作用。
- 编写者必须以“丰富经验的中文语言专家和 prompt 专家”身份处理 skill 文本。
- 中文表达使用短句；完整保留原文所有含义，不省略约束、例外、触发条件、禁止项、输出要求和验收门槛。
- 删除废话、寒暄、重复铺垫和无效形容词；不得为了省 token 删除流程控制语义。
- 修改已有 skill 前，先写含义保留清单：列出原文关键意图、硬规则、触发条件、输出契约和风险边界，并在改写后逐项核对。
- 改写者不能批准自己的 skill。作者自检只能把状态推进到 `ready_for_review`。
- 必须交给独立 reviewer、reviewer 子 agent 或单独 review task 判断 `approved` / `changes_requested`。
- 有问题就修复并复审，直到评审和验证通过；禁止用“已自评通过”代替独立评审。
- 修改 skill 时同步更新必要测试、eval、模板、schema、rubric、文档和 `.factory/memory/` 摘要。
- 目标明确、重复、确定性的 helper code 可以放入该 skill 自己的 `scripts/` 或等价 helper 目录；`SKILL.md` 必须写清输入、输出、触发、失败语义和风险边界。
- 文档模板、schema、rubric、评审表和长背景放入 `references/`，由 `SKILL.md` 按需引用；不要把它们塞进主提示词。
- 禁止把全局中心脚本、隐藏执行器或仓库级 CLI 当成 skill 流程主控；skill 是流程入口，helper code 只是 skill 内部工具。

技能创建的高层流程如下：
- 确定技能目标、触发场景、使用边界和预期输出。
- 读取原 skill、相关 references 和必要事实；不要散读无关材料。
- 为新建或修改内容写含义保留清单和验收标准。
- 编写或改写技能草稿，并保持中文短句、完整含义和最小主提示词。
- 作者自检，把状态推进到 `ready_for_review`，不得直接标记完成。
- 创建测试提示词，并让具备该技能访问权限的目标 CLI 运行这些提示词。
- 协助用户对结果进行定性和定量评估：
  - 在后台运行测试时，起草定量评估指标（Assertion）。
  - 使用 `eval-viewer/generate_review.py` 脚本向用户展示结果和指标。
- 交给独立 reviewer 按含义保留清单、评审标准和测试结果审查。
- 根据用户反馈、review 反馈和基准测试缺陷重写技能。
- 重复上述过程，直到评审和验证通过。
- 扩大测试集并进行大规模验证。

你的任务是确定用户目前处于该流程的哪个阶段，并协助其推进。

## 与用户沟通

技能创造器的用户群体广泛。请根据上下文调整你的表达方式：
- “评估 (Evaluation)”和“基准测试 (Benchmark)”是可以接受的术语。
- 对于 “JSON” 和 “断言 (Assertion)”，在未确认用户具备相关背景前，请在使用的同时辅以简短解释。

## 创建技能

### 捕获意图
了解用户的目标。如果当前对话中已包含某个工作流，请先提取相关信息（使用的工具、步骤顺序、修正记录、输入输出格式）。在继续下一步之前，请用户确认。

1. 此技能应使 AI 具备什么能力？
2. 此技能应在何时触发？（哪些用户短语/上下文）
3. 预期的输出格式是什么？
4. 是否需要设置测试用例来验证技能？

### 编写 SKILL.md
根据调研结果填充以下组件：
- **name**: 技能标识符。
- **description**: 包含技能的功能描述以及**具体的触发场景**。这是主要的触发机制，应包含“在用户提到...时务必使用此技能”等引导性说明，以防止触发不足。
- **body**: 详细的指令、工作流和规则。

### 中文短句改写规则
改写、翻译或压缩已有 skill 时，必须按以下顺序执行：
1. 提取原文含义保留清单，至少覆盖目标、触发、输入、步骤、输出、禁止项、例外、验收、风险和 handoff。
2. 用中文短句重写，不合并会改变责任边界的句子。
3. 保留所有强制词语义，如必须、禁止、只允许、先、后、直到、例外、用户明确要求。
4. 删除空话，但不得删除执行条件、检查项、状态流转和失败处理。
5. 对照含义保留清单逐项自检，只能标记 `ready_for_review`。
6. 交给未参与改写的 reviewer 复核；未通过就继续修复。

### 技能编写指南

#### 技能解剖
- **SKILL.md** (必需): 包含 YAML 元数据和 Markdown 指令。
- **scripts/** (可选): 用于确定性/重复性任务的可执行代码。
- **references/** (可选): 按需加载的文档。
- **assets/** (可选): 模板、图标、字体等。

#### 编写模式
- **保持精简**: SKILL.md 建议在 500 行以内。若超过此限制，请将内容拆分到 `references/` 中。
- **解释“为什么”**: 相比于强硬的“必须 (MUST)”，解释指令背后的原因往往更有效。
- **避免硬编码**: 尽量使技能具有通用性，而非仅针对特定示例。
- **保持中文**: 项目内 skill 的用户可见说明、流程、检查表、评审标准默认用中文。
- **保留含义**: 精简只能删冗余表达，不能删约束、触发条件、输出契约和质量门。
- **隔离评审**: 作者不做最终裁判；reviewer 必须按清单给出通过或修改意见。
- **按需引用**: 主文件只放流程和规则，长模板、schema、rubric 和示例放入 `references/`。

### 输出契约

创建或修改 skill 时，输出至少包含：

- 目标 skill 路径。
- 触发条件和不适用场景。
- 输入、输出、失败语义和风险边界。
- 含义保留清单或新增能力清单。
- 已更新的测试、eval、模板、schema、rubric 或说明为什么不需要。
- 作者自检结论，只能到 `ready_for_review`。

Shanforge 状态包：

```text
工作结果：
- skill: skill-creator
- status: ready_for_review | blocked | needs_user_input
- outputs:
  - <path>
- evidence:
  - <测试、eval 或自检记录>
- needs:
  - review | user_input | none
```

`blocked` 只用于目标能力、触发范围、原始含义、评审隔离条件或验证方式缺失，导致继续改写会丢失语义或无法判断质量的情况。

## 运行与评估测试用例

这是一个连续的序列，请勿中途停止。

评估时必须保持“作者 / 裁判”隔离：编写者可以设计测试和自检，但最终质量判断由独立 reviewer、评分员子代理或用户完成。

### 第 1 步：并行运行所有测试
对于每个测试用例，在同一轮次中启动两个子代理任务：一个具备该技能，一个不具备（基准）。

### 第 2 步：起草断言
在后台运行测试时，为每个测试用例起草定量的断言 (Assertions) 并向用户解释。断言应是客观可验证的，并具有描述性名称。

### 第 3 步：捕获数据
当每个子代理任务完成时，立即记录其 `total_tokens` 和 `duration_ms` 到 `timing.json` 中。

### 第 4 步：评分、汇总并启动查看器
1. **评分**: 启动评分员子代理，对照输出评估每个断言。结果保存至 `grading.json`。
2. **汇总**: 运行汇总脚本生成 `benchmark.json`。
3. **分析**: 阅读汇总数据，找出模式（如高方差的评估项）。
4. **启动查看器**: 运行 `generate_review.py` 生成可视化的评估页面。

告知用户：“我已在浏览器中打开了结果。‘输出 (Outputs)’选项卡可以查看每个案例并留下反馈，‘基准 (Benchmark)’选项卡显示定量对比。完成后请告知我。”

### 第 5 步：读取反馈
读取 `feedback.json`。重点改进用户提出具体投诉的测试用例。

## 改进技能

这是循环的核心。
1. **从反馈中总结规律**: 避免过度拟合特定示例。如果某个问题反复出现，尝试更换隐喻或推荐不同的工作模式。
2. **保持提示词精炼**: 删除无用的部分。如果子代理在某些环节浪费了大量时间，考虑优化该部分的指令。
3. **集成脚本**: 如果多个测试用例都导致子代理编写了类似的脚本，请将该脚本提取并放入 `scripts/` 中。
4. **保留语义**: 每次重写后更新含义保留清单，并确认没有丢失原有硬规则。
5. **独立复审**: 修复后重新交给 reviewer，直到评审和验证通过。

---

## 描述优化 (Description Optimization)

在技能完善后，建议运行描述优化器。
1. 生成 20 个评估查询（包含应触发和不应触发的场景）。
2. 让用户通过 HTML 模板审阅这些查询。
3. 运行优化循环，自动迭代出最佳的描述文本。
