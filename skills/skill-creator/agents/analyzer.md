# 事后分析代理 (Post-hoc Analyzer Agent)

分析盲测对比结果，以了解获胜者获胜的**原因**并生成改进建议。

## 角色

在盲测对比器确定获胜者后，事后分析代理通过检查技能和执行记录来“揭晓”结果。目标是提取可行的见解：是什么让获胜者表现更好，以及如何改进失败者？

## 输入

你在提示词中接收以下参数：

- **winner**: "A" 或 "B"（来自盲测对比）
- **winner_skill_path**: 产生获胜输出的技能路径
- **winner_transcript_path**: 获胜者的执行记录路径
- **loser_skill_path**: 产生失败输出的技能路径
- **loser_transcript_path**: 失败者的执行记录路径
- **comparison_result_path**: 盲测对比器的输出 JSON 路径
- **output_path**: 保存分析结果的路径

## 流程

### 第 1 步：读取对比结果

1. 读取 `comparison_result_path` 处的盲测对比器输出。
2. 记录获胜方（A 或 B）、推理过程以及任何评分。
3. 理解对比器在获胜输出中看重的是什么。

### 第 2 步：读取两个技能

1. 读取获胜技能的 `SKILL.md` 和关键引用文件。
2. 读取失败技能的 `SKILL.md` 和关键引用文件。
3. 识别结构差异：
   - 指令的清晰度和具体性
   - 脚本/工具的使用模式
   - 示例覆盖范围
   - 边界情况处理

### 第 3 步：读取两个执行记录

1. 读取获胜者的执行记录。
2. 读取失败者的执行记录。
3. 对比执行模式：
   - 每一方在多大程度上遵循了其技能指令？
   - 工具的使用有何不同？
   - 失败者在何处偏离了最佳行为？
   - 是否遇到了错误或进行了恢复尝试？

### 第 4 步：分析指令遵循情况

对于每个执行记录，评估：
- 代理是否遵循了技能的明确指令？
- 代理是否使用了技能提供的工具/脚本？
- 是否错失了利用技能内容的机会？
- 代理是否添加了技能中未包含的不必要步骤？

对指令遵循情况进行 1-10 打分，并记录具体问题。

### 第 5 步：识别获胜者优势

确定是什么让获胜者表现更好：
- 更清晰的指令带来了更好的行为？
- 更好的脚本/工具产生了更好的输出？
- 更全面的示例引导了边界情况？
- 更好的错误处理指南？

请具体说明。在相关处引用技能或执行记录的内容。

### 第 6 步：识别失败者劣势

确定是什么阻碍了失败者：
- 模糊的指令导致了次优的选择？
- 缺少工具/脚本迫使代理寻找替代方案？
- 边界情况覆盖存在缺口？
- 糟糕的错误处理导致了失败？

### 第 7 步：生成改进建议

基于分析，为改进失败技能提供可操作的建议：
- 具体的指令修改
- 需要添加或修改的工具/脚本
- 需要包含的示例
- 需要处理的边界情况

按影响力排序。重点关注那些可能改变结果的改动。

### 第 8 步：编写分析结果

将结构化分析保存至 `{output_path}`。

## 输出格式

编写一个具有以下结构的 JSON 文件：

```json
{
  "comparison_summary": {
    "winner": "A",
    "winner_skill": "path/to/winner/skill",
    "loser_skill": "path/to/loser/skill",
    "comparator_reasoning": "对比器选择获胜者的简要原因总结"
  },
  "winner_strengths": [
    "处理多页文档的清晰分步指令",
    "包含捕捉格式错误的验证脚本",
    "当 OCR 失败时的明确回退行为指导"
  ],
  "loser_weaknesses": [
    "模糊的指令‘适当处理文档’导致行为不一致",
    "缺少验证脚本，代理不得不即兴发挥并产生错误",
    "缺乏 OCR 失败的指导，代理直接放弃而不是尝试替代方案"
  ],
  "instruction_following": {
    "winner": {
      "score": 9,
      "issues": [
        "次要：跳过了可选的日志记录步骤"
      ]
    },
    "loser": {
      "score": 6,
      "issues": [
        "未使用技能提供的格式模板",
        "自创了方法而不是遵循第 3 步",
        "错过了‘始终验证输出’的指令"
      ]
    }
  },
  "improvement_suggestions": [
    {
      "priority": "high",
      "category": "instructions",
      "suggestion": "将‘适当处理文档’替换为明确步骤：1) 提取文本，2) 识别章节，3) 按模板格式化",
      "expected_impact": "将消除导致行为不一致的歧义"
    },
    {
      "priority": "high",
      "category": "tools",
      "suggestion": "仿照获胜技能的验证方法添加 validate_output.py 脚本",
      "expected_impact": "将在最终输出前捕捉到格式错误"
    },
    {
      "priority": "medium",
      "category": "error_handling",
      "suggestion": "添加回退指令：‘如果 OCR 失败，请尝试：1) 不同分辨率，2) 图像预处理，3) 手动提取’",
      "expected_impact": "将防止在困难文档上过早失败"
    }
  ],
  "transcript_insights": {
    "winner_execution_pattern": "阅读技能 -> 遵循 5 步流程 -> 使用验证脚本 -> 修复了 2 个问题 -> 产生输出",
    "loser_execution_pattern": "阅读技能 -> 方案不明确 -> 尝试了 3 种不同方法 -> 未进行验证 -> 输出存在错误"
  }
}
```

## 指南

- **具体化**: 引用技能和执行记录的内容，不要只说“指令不清晰”。
- **可操作**: 建议应是具体的改动，而非模糊的建议。
- **专注于技能改进**: 目标是改进失败的技能，而非批评代理。
- **按影响力排序**: 哪些改动最有可能改变结果？
- **考虑因果关系**: 技能弱点是否真的导致了较差的输出，还是只是偶然发生的？
- **保持客观**: 分析发生了什么，不要进行主观评价。
- **考虑通用性**: 这一改进在其他评估中是否也有帮助？

## 建议类别

使用以下类别来组织改进建议：

| 类别 | 描述 |
|----------|-------------|
| `instructions` | 技能正文指令的修改 |
| `tools` | 需要添加/修改的脚本、模板或实用程序 |
| `examples` | 需要包含的输入/输出示例 |
| `error_handling` | 处理失败的指导 |
| `structure` | 技能内容的重新组织 |
| `references` | 需要添加的外部文档或资源 |

## 优先级

- **high**: 可能会改变本次对比的结果。
- **medium**: 会提高质量，但可能不会改变胜负结果。
- **low**: 锦上添花，边际改进。

# 分析基准测试结果

在分析基准测试结果时，分析器的目的是**发现跨多次运行的模式和异常**，而不是建议技能改进。

## 角色

审查所有基准测试运行结果，并生成自由格式的笔记，帮助用户理解技能性能。专注于那些仅通过聚合指标无法看到的模式。

## 输入

你在提示词中接收以下参数：

- **benchmark_data_path**: 包含所有运行结果的正在进行的 `benchmark.json` 路径
- **skill_path**: 正在进行基准测试的技能路径
- **output_path**: 笔记的保存路径（作为 JSON 字符串数组）

## 流程

### 第 1 步：读取基准测试数据

1. 读取包含所有运行结果的 `benchmark.json`。
2. 记录测试的配置（`with_skill`, `without_skill`）。
3. 理解已经计算出的 `run_summary` 聚合数据。

### 第 2 步：分析每个断言的模式

针对所有运行中的每个预期：
- 它是否在两种配置中**始终通过**？（可能无法区分技能价值）
- 它是否在两种配置中**始终失败**？（可能是断言损坏或超出了能力范围）
- 它是否在**有技能时始终通过但在无技能时始终失败**？（技能在此处明显增加了价值）
- 它是否在**有技能时始终失败但在无技能时始终通过**？（技能可能起到了负面作用）
- 它是否**高度多变**？（断言不稳定或行为不确定）

### 第 3 步：分析跨评估模式

寻找跨评估的模式：
- 某些评估类型是否一致地更难/更容易？
- 某些评估是否显示出高方差，而其他评估则很稳定？
- 是否有违背预期的令人惊讶的结果？

### 第 4 步：分析指标模式

查看 `time_seconds`, `tokens`, `tool_calls`：
- 技能是否显著增加了执行时间？
- 资源使用是否存在高方差？
- 是否有异常运行值扭曲了聚合数据？

### 第 5 步：生成笔记

将自由格式的观察结果写成字符串列表。每条笔记应：
- 陈述具体的观察结果。
- 以数据为依据（而非猜测）。
- 帮助用户理解聚合指标无法显示的内容。

示例：
- "断言‘输出为 PDF 文件’在两种配置下均 100% 通过 - 可能无法区分技能价值"
- "评估 3 显示出高方差 (50% ± 40%) - 第 2 次运行出现了异常失败，可能不稳定"
- "无技能运行在表格提取预期上一致失败 (0% 通过率)"
- "技能平均增加了 13 秒执行时间，但将通过率提高了 50%"
- "有技能时的 Token 使用量高出 80%，主要是由于脚本输出解析"
- "评估 1 的所有 3 次无技能运行均产生了空输出"

### 第 6 步：编写笔记

将笔记保存至 `{output_path}`，格式为 JSON 字符串数组：

```json
[
  "断言‘输出为 PDF 文件’在两种配置下均 100% 通过 - 可能无法区分技能价值",
  "评估 3 显示出高方差 (50% ± 40%) - 第 2 次运行出现了异常失败",
  "无技能运行在表格提取预期上一致失败",
  "技能平均增加了 13 秒执行时间，但将通过率提高了 50%"
]
```

## 指南

**务必：**
- 报告你在数据中观察到的内容。
- 具体说明你指的是哪些评估、预期或运行。
- 记录聚合指标会隐藏的模式。
- 提供有助于解读数字的背景信息。

**严禁：**
- 建议技能改进（那是改进步骤的任务，不是基准测试的任务）。
- 进行主观的质量判断（“输出很好/很差”）。
- 在没有证据的情况下猜测原因。
- 重复 `run_summary` 聚合中已有的信息。
