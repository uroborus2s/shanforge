## 触发条件

- 支付重复入账、越权访问、订单/库存数据损坏；
- P0 核心流程错误率或延迟超过已批准阈值；
- 数据迁移导致不可接受的读写错误；
- 客户端新版本与服务端契约不兼容且无法通过兼容层止损。

## 回滚顺序

1. 发布负责人宣布冻结变更并记录事件时间线。
2. 关闭新功能开关或停止增量流量，保留读路径。
3. 服务端回到上一个已验证镜像；客户端通过远程配置降级，不假设应用商店能立即回滚。
4. 只执行已演练的数据恢复方案。已经产生的订单、支付和审计事实不得用普通降级迁移删除。
5. 验证登录、服务查询、订单读取、支付对账和后台只读能力。
6. 对账确认后再决定恢复流量或继续应急处置。

## 数据策略

- 数据库变化优先采用向后兼容的 expand/contract，不依赖破坏性回滚。
- 新字段先可空或有明确默认，再回填，最后收紧约束。
- 支付、退款、订单事件采用补偿和对账，不通过直接修改历史记录“回滚”。
- 回滚前保存迁移版本、备份标识、受影响订单范围和校验摘要。

## 验证清单

| 检查 | 通过条件 |
|---|---|
| 服务健康 | 核心实例健康且依赖连接正常 |
| 数据兼容 | 旧版本可读取当前数据，迁移版本符合预期 |
| 订单读取 | 抽样订单状态和事件链一致 |
| 资金对账 | 支付平台、支付流水和订单状态无新增差异 |
| 权限 | 无权限账户仍被拒绝，高风险操作审计可查 |

## 决策记录

正式执行必须记录触发原因、指挥人、起止时间、命令或流水线、验证证据、数据影响和恢复决策；样例不包含真实执行记录。
