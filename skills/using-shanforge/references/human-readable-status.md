# 人类可读状态正文合同

本合同保留三段式人类响应外壳：共享状态头和按工作类型正文都放在“处理结果”部分。先用业务语言说明结论；内部 ID、Gate、路径和命令只作为末尾技术记录，不替代正文。

## 共享状态头

项目化进度更新先回答“项目是否完成”，再说明总体阶段与当前活动、本批剩余、已批准产品剩余、未知/未验证与未开始、遗漏核对、阻塞和唯一下一动作。缺完整基线时写“未知”，不得估算。

- 开发 / 计划的事实源只能是已批准 WBS、TaskCard 和 ledger。
- 逐项区分已完成、进行中、未开始和阻塞；已完成项必须写可观察结果和验证状态。
- system、评审、提交等任务不得算作产品功能进度；可单列为治理或交付状态。
- 没有完整 WBS 或已批准分母时，明确写“无法计算”，不得猜测百分比或分母。
- 仅在已批准分母可得时，才汇总 WBS 项；剩余范围仍须逐项说明，不能只报百分比。
- `scope_remaining` 只表示当前已授权批次；总体阶段和已批准产品剩余由总控从完整项目事实生成，不得把本批完成写成产品完成。
- 遗漏核对写基线定位/版本、`checked | incomplete | not_checked` 及未映射或未知项；普通本批收口的 `not_checked` 不阻塞继续，但不等于已验收。
- 总体阶段只能从产品生命周期事实读取或推断，并标明依据；缺事实写“无法确认”。状态查询、代码评审、提交或修 bug 只说明当前活动，不能自动成为总体阶段。
- 用户可见遗漏核对写“已核对 | 核对不完整 | 尚未核对”；基线不存在不得写“已核对”，已有已知缺陷不得把全部状态写成未知。
- 回复必须有一个可执行的唯一下一动作；用户只问状态时写建议，不因此自动改业务。“无需回复”只说明是否需要用户输入，不能代替下一动作。产品真正完成可以无后续开发动作；发布另据事实说明。
- 已知本批缺口可确定“产品尚不能交付”；缺完整产品基线时写“已知缺口：…；完整产品剩余未知”，不得把本批缺口冒充完整产品剩余。进行中的 bug 修复是进行中，不属于未知/未验证与未开始。

## 进度事实对账边界

所有展示的 WBS/产品进度变化必须先与已批准 WBS、TaskCard 和 ledger 对账。

| 输入事实 | 总控处理 | 对产品完成度的影响 |
|---|---|---|
| 已批准 WBS、TaskCard 和 ledger 可匹配 | 映射为对应 WBS 项状态 | 可推进该项产品完成度 |
| worker facts 无法匹配 | 仅作为本轮执行观察或技术记录 | 不得推进产品完成度 |

## 按工作类型正文

### 开发 / 计划

按 WBS 与 TaskCard 展示四态、每个已完成项的可观察结果和验证状态；说明当前实现或计划正在改变什么，以及哪些已批准项尚未开始或被阻塞。

### 测试

按完整测试基线与本轮报告说明覆盖范围、总数和通过、失败、错误、阻塞、跳过、未运行、取消；局部通过只能表述为局部通过。失败或错误写测试 ID、关联功能、可观察现象和当前归因；根因未知写“待调查”。

### Bug / 修复

说明现象、影响、复现、直接原因、根源原因、事实 owner、风险、修复状态和回归验证。每个修复位置再逐项给出 `file`、`symbol`、`change`、`reason` 和 `verification`；没有函数边界时写实际模块、配置项或文档章节，不得伪造函数名。根因未定位时只写已知事实与唯一诊断动作；是否创建 Bug TaskCard 由适用的修复任务卡决策合同决定。

### 评审 / 交付

说明评审或交付结论、发现和验证证据，以及对已批准产品范围的影响；不得把 review、verification、commit 或 system 状态写成新增产品功能或项目完成。

### 技术评估

按“需求 → 现象 → 代码 → 原因 → 影响 → 建议”解释技术问题：需求依据写目标、验收和约束；现象写实际、期望、触发和证据，纯静态审查要注明；代码证据必须给真实 `file`、`symbol` 及控制流或数据流；因果链写代码行为如何导致现象和需求影响，并区分直接原因、根源原因和未知。再给影响与满足度结论、建议修改位置和验证方法。不得只写“架构不合理、耦合高、建议重构”，不得用评分、内部 ID、路径或术语清单替代解释；建议仍是建议，不得冒充已修复。

## Bug 示例

### 处理结果

现象：状态回复只显示内部状态码。影响：用户无法判断开发进度和测试结论。复现：执行状态更新后阅读回复。直接原因：回复缺少面向用户的事实字段。根源原因：待调查。owner：状态回复合同。风险：错误进度判断。Bug TaskCard 决策：当前整改 TaskCard 已覆盖，不新建。

### 验证与风险

尚未验证根源原因；在根源原因明确前不得声称已修复。

### 下一步

唯一下一动作：调查状态回复遗漏事实字段的根源原因；无需回复。
