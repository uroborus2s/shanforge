# 人类可读状态正文合同

本合同保留三段式人类响应外壳：共享状态头和按工作类型正文都放在“处理结果”部分。先用业务语言说明结论；内部 ID、Gate、路径和命令只作为末尾技术记录，不替代正文。

## 共享状态头

项目化进度更新必须说明当前阶段、当前任务、已完成结果、剩余范围、阻塞和唯一下一动作。

- 开发 / 计划的事实源只能是已批准 WBS、TaskCard 和 ledger。
- 逐项区分已完成、进行中、未开始和阻塞；已完成项必须写可观察结果和验证状态。
- system、评审、提交等任务不得算作产品功能进度；可单列为治理或交付状态。
- 没有完整 WBS 或已批准分母时，明确写“无法计算”，不得猜测百分比或分母。
- 仅在已批准分母可得时，才汇总 WBS 项；剩余范围仍须逐项说明，不能只报百分比。

## 进度事实对账边界

所有展示的 WBS/产品进度变化必须先与已批准 WBS、TaskCard 和 ledger 对账。

| 输入事实 | 总控处理 | 对产品完成度的影响 |
|---|---|---|
| 已批准 WBS、TaskCard 和 ledger 可匹配 | 映射为对应 WBS 项状态 | 可推进该项产品完成度 |
| worker facts 无法匹配 | 仅作为本轮执行观察或技术记录 | 不得推进产品完成度 |

## 按工作类型正文

### 开发 / 计划

按 WBS 与 TaskCard 展示四态、每个已完成项的可观察结果和验证状态；说明当前实现或计划正在改变什么，以及哪些已批准项尚未开始或被阻塞。

### 测试

按完整测试基线与本轮报告说明覆盖范围、总数和通过、失败、错误、阻塞、跳过、未运行、取消；局部通过只能表述为局部通过。失败或错误写测试 ID、关联功能、可观察现象和当前归因；根因未知写“待调查”。

### Bug / 修复

说明现象、影响、复现、直接原因、根源原因、事实 owner、风险、修复状态和回归验证。根因未定位时只写已知事实与唯一诊断动作；是否创建 Bug TaskCard 由适用的修复任务卡决策合同决定。

### 评审 / 交付

说明评审或交付结论、发现和验证证据，以及对已批准产品范围的影响；不得把 review、verification、commit 或 system 状态写成新增产品功能或项目完成。

## 技术记录

正文之后可以附最小技术记录：相关内部 ID、Gate、路径、命令和原始状态。它只能支撑可追溯性，不能替代共享状态头、工作类型正文或用户可见的唯一下一动作。
